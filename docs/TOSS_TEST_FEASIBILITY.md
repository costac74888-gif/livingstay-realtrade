# 토스 테스트 연동 확인과 현재 제한

## 결론

토스 공식 문서에는 JavaScript SDK 결제창과 서버 승인·조회·취소 API를
이용하는 직접 연동 방식이 있다. 내장 커넥터 목록에 없다는 이유만으로
Replit에서 기술적으로 불가능하다고 판단할 근거는 없다.

다만 현재 에이전트가 사용할 수 있는 결제 연동 절차는
Shopify·Stripe·Whop·RevenueCat으로 제한된다. 토스 직접 구현으로
이 제한을 우회할 수 없다. 이는 토스 테스트키 부족이나 확인된 Replit
네트워크 차단 때문이 아니다. 실제 토스 API 연결은 실행하지 않았다.
다른 PG로 교체하지 않는다.

## 사용자 비밀 설정

향후 직접 연동을 구현하는 담당자가 사용할 권장 설정명은 다음과 같다.
현재 앱에서 이 설정을 읽는 토스 연동 코드는 구현되어 있지 않다.
따라서 키를 저장하는 것만으로 결제가 연결되지는 않는다.

- `TOSS_TEST_CLIENT_KEY`: 선택한 SDK 상품과 맞는 테스트 클라이언트키.
- `TOSS_TEST_SECRET_KEY`: 같은 상점·상품의 테스트 시크릿키.

Replit 프로젝트의 **Tools → Secrets → Secrets**에서 설정한다.
Configurations, 채팅, 소스 파일, Git 또는 로그에 값을 넣지 않는다.
개발 검증에만 사용하고 운영 설정에는 추가하지 않는다.
이번 작업에서는 키를 수집하거나 존재 여부·값을 조회하지 않았다.

클라이언트키는 SDK를 초기화할 때 브라우저에 제공되는 값이다.
시크릿키는 서버에만 두며 브라우저나 성공 리다이렉트 URL로 전달하지 않는다.
키 종류는 연동 방식에 따라 다르므로 발급받은 상품의 키 쌍을 확인해야 한다.
공식 API 문서는 테스트 시크릿키와 라이브 시크릿키를 구분한다.

## 직접 연동 담당자의 수동 작업

1. 별도의 개발 DB·테스트 주문·테스트 재고와 알림 차단 환경을 준비한다.
2. 공식 SDK 상품과 키 종류를 맞추고 개발 도메인 및 성공·실패 경로를 확인한다.
3. 주문 금액을 서버 원장에 고정하고 승인 전 주문·금액·소유자를 검증한다.
4. 서버에서만 승인 API를 호출하고 공급자 응답과 예약·결제 원장을 연결한다.
5. 중복 승인·재시도·webhook 중복을 원장과 멱등성 기준으로 검증한다.
6. 테스트 결제의 취소 결과와 예약 재고 복구를 함께 확인한다.
7. 공급자 증거와 모의 증거를 분리해 기록한다.

위 목록은 필요한 작업 설명이지 구현·테스트 성공 기록이 아니다.
API 출발지 제한, 실제 테스트 상점 설정 및 계약 조건은 미검증이다.

공식 환경 문서에 따르면 지급대행 테스트 셀러는 유효한 사업자번호의
법인사업자만 등록할 수 있고, 테스트 KYC를 수행할 수 없어 `APPROVED`
상태로 전환할 수 없다. 라이브 지급대행 요청에는 수수료가 발생한다.
이번 범위에서는 라이브 지급대행을 호출하지 않는다. 해당 계약과 보증금
처리 적합성은 사용자 상점의 실제 계약을 확인하기 전에는 확정할 수 없다.

## 실제 공급자 검증 상태

| 항목 | 상태 |
| --- | --- |
| 토스 결제창·승인·예약/결제 내역 반영 | 미실행 |
| 결제 성공·실패·사용자 취소 | 미실행 |
| 금액 불일치·중복 승인·재시도 | 미실행 |
| 중복 webhook·테스트 취소/환불·재고 복구 | 미실행 |
| 보증금·호스트 정산/지급대행 | 계약·지원 범위 미확인, 완료 아님 |

기존 계좌 입금 멤버십의 가상 승인 검사는 토스 결제 검증이 아니다.
실결제·실제 환불·정산·발송·운영 DB 변경·main 병합·운영 배포는
여전히 승인 범위 밖이다. 통합 Preview와 Phase18 완료를 표시하지 않는다.
