## 1. 전체 구조와 적용 범위

### 1-1. 구축 목적

Replit 게시 환경에서 일부 공공 API의 연결 지연·실패가 발생한 사례가 있어, 고정 주소의 중계서버를 통해 지정된 API만 호출하도록 설계했습니다. 중계 도입이 모든 공공 API 장애를 해결하거나 모든 프로젝트의 운영 전환을 완료했다는 뜻은 아닙니다.

```text
Replit 프로젝트
  → HTTPS / X-Relay-Token / X-Relay-Purpose
relay.homenstay.com
  → 허용된 공공 API만 호출
공공 API 공급자
```

## 3. DNS 설정

1. 도메인 관리 화면에서 homenstay.com의 DNS 관리로 이동합니다.
2. A 레코드의 호스트를 relay로 지정하고, 현재 호스팅에 할당된 서버 IP를 입력합니다. v1의 IP는 180.70.116.132입니다.
3. 저장 후 DNS 응답을 확인합니다. 5~30분은 원본의 예상 대기이며, 실제 전파 시간은 TTL·캐시·DNS 운영 상태에 따라 달라집니다.
4. PowerShell에서 다음 명령을 실행합니다.

```text
nslookup relay.homenstay.com
```

응답 IP가 현재 서버 IP와 일치하는지 확인합니다. 불필요한 AAAA 레코드가 다른 서버를 가리키는지도 점검합니다. 일반적인 Caddy 공개 HTTPS 자동 발급에서는 도메인 연결과 인증 방식에 필요한 외부 접근이 정상이어야 합니다. 인증서 발급 실패 시 DNS만 원인으로 단정하지 않고 방화벽·인증서 발급 로그도 확인합니다.

## 4. 서버 접속과 SSH 지문 확인

### 4-1. 최초 접속

호스팅 콘솔에서 현재 IP와 접속 계정을 확인합니다. v1 예시는 root 접속입니다. 운영 안정화 후에는 전용 관리 계정과 SSH 키 사용을 권장합니다.

```text
ssh root@180.70.116.132
```

처음 표시된 호스트 지문은 무조건 승인하지 않습니다. Cafe24 관리 콘솔의 서버 콘솔 등 별도로 신뢰할 수 있는 경로에서 실제 지문을 확인하고 대조합니다.

```text
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

PC에서 안내된 키 종류가 ED25519인지도 확인합니다. 다른 종류라면 대응하는 서버 공개키의 지문을 비교합니다. 일치 확인 후 영문 입력 상태에서 yes를 입력합니다. 비밀번호 입력 문자가 화면에 보이지 않는 것은 정상입니다.

### 4-2. 지문 변경 경고

REMOTE HOST IDENTIFICATION HAS CHANGED가 나오면 우선 접속을 중단합니다. 재설치·호스팅 이전 등 정상 변경인지 관리 콘솔에서 확인하고, 새 지문을 신뢰 가능한 경로로 대조합니다.

정상 변경을 확인한 뒤에만 PC PowerShell에서 기존 기록을 삭제합니다.

```text
ssh-keygen -R 180.70.116.132
```

도메인으로 접속했다면 해당 도메인 기록도 따로 확인합니다. 기록 삭제는 서버 신원 검증이 아닙니다. 삭제 후 재접속할 때 새 지문을 대조한 뒤 승인합니다.

### 4-3. 방화벽

원본의 기본 허용 포트는 22/80/443입니다. 호스팅 방화벽과 서버 ufw를 모두 점검합니다. 가능하면 SSH 접근을 관리 IP로 제한합니다. 방화벽 변경 전 현재 SSH 연결과 호스팅 콘솔 복구 경로를 확보합니다.

## 5. 설치 파일 복사·설치·권한 점검

### 5-1. PC에서 복사

아래 명령은 SSH 서버 화면이 아니라 PC PowerShell에서 실행합니다. 파일 경로는 실제 위치로 바꿉니다.

```text
scp "C:\경로\install-single.sh" root@180.70.116.132:/root/
```

설치 파일의 출처와 수정 내용을 확인합니다. 기존 서버 업데이트라면 설정·DB·직전 릴리스 복구 방법을 먼저 확인합니다.

### 5-2. 서버에서 실행

```text
bash /root/install-single.sh
```

v1의 설치 설명에는 패키지 설치, relay 사용자 생성, 앱 배치, venv 구성, systemd·Caddy·ufw·fail2ban·자동 보안업데이트 설정이 포함되어 있습니다. 이번 개정에서는 설치 파일 원본을 검증하지 않았으므로, 실행 전 실제 스크립트가 수행하는 작업과 기존 설정 덮어쓰기 여부를 확인합니다.

### 5-3. 권한 관련 실패의 정확한 해석

v1은 “umask 027 때문에 root만 읽을 수 있음”이라고 설명했으나, 이는 정확하지 않습니다. 일반적인 생성 모드에서 umask 027은 파일 640·디렉터리 750을 만들며 소유 그룹에는 읽기·탐색 권한이 남습니다.

실제 실패 원인은 파일·상위 디렉터리의 소유자·그룹·권한 때문에 서비스 계정 relay가 필요한 파일을 읽거나 경로를 탐색하지 못한 경우로 확인해야 합니다. systemd 로그와 실제 서비스 계정, /opt/relay 및 릴리스·venv 경로를 함께 대조합니다.

v1에 기록된 임시 수정 예시는 다음과 같습니다.

```text
chmod 0755 /opt/relay
chmod -R a+rX "$RELEASE"
```

주의: 두 줄이 모든 권한 문제를 해결한다고 보장하지 않습니다. $RELEASE가 실제 릴리스 경로인지 확인해야 하며, a+rX는 다른 로컬 사용자에게도 읽기·디렉터리 탐색 권한을 부여할 수 있습니다. 인증 설정·토큰·DB 등 민감 파일에 일괄 적용하지 않습니다. 서비스 계정에 필요한 최소 권한을 부여하는 방식으로 설치 파일을 수정하고 검증합니다.

### 5-4. 설치 확인

```text
systemctl status relay --no-pager
systemctl status caddy --no-pager
curl -fsS https://relay.homenstay.com/health
```

서비스 active와 /health 정상 응답은 기본 기동·HTTPS 확인입니다. 공공 API 허용 목록, 토큰 권한, 공급자 정상 응답, DB 적재까지 성공했다는 뜻은 아닙니다. 그 검증은 7장과 8장에서 별도로 수행합니다.

## 6. 프로젝트·용도별 토큰

v1 서버 설계는 프로젝트 및 realtime/batch 용도별 토큰과 해시 저장 방식입니다. 실제 서버 구현과 발급 명령은 현장 확인 후 사용합니다. 해시만 저장하는 구현이라면 분실한 원문 토큰을 복구할 수 없으므로 재발급·교체합니다.

| 프로젝트 이름 | 실제 프로젝트 | 원본 기준 필요한 용도 |
|---|---|---|
| gwanri | 관리의달인 HP 리뉴얼 | realtime |
| homenstay | 홈앤스테이 | realtime + batch |
| assetmanager | ASSET MANAGER | realtime, 원본에는 미발급으로 기록 |

```text
relay-admin token create gwanri
relay-admin token create homenstay
relay-admin token create homenstay --purpose batch
relay-admin token create assetmanager
```

위 명령은 원본 예시입니다. 기존 토큰이 있으면 확인 없이 중복 발급하지 않습니다. 토큰 출력은 안전한 서버 터미널에서만 확인하고, 해당 프로젝트의 올바른 환경 Secrets에 즉시 저장합니다. 실제 값을 채팅·메모장·공유 문서에 붙여 넣지 않습니다.

분실·노출 시 rotate, 폐기 시 revoke를 사용합니다. 실제 명령 옵션과 기존 토큰 폐기 시점은 서버 도움말·구현으로 확인합니다. batch 교체에서는 해당 용도를 명시하고, 교체 후 관련 웹·예약 배포 설정을 갱신하여 새 실행에 적용합니다.

## 7. 실제 공공 API 경로 검증

```text
relay-admin verify bldg-hub
```

v1에 기재된 검증 명령입니다. 인증값은 숨김 입력창에서만 입력하고, 로그·명령행 인자·셸 기록에 남기지 않습니다. 공급자가 요구하는 디코딩된 인증키 여부도 명령 안내와 API 사양을 대조합니다.

v1에는 force_refresh 권한이 있는 토큰이 필요하며 임시 허용 후 복구했다고 기록되어 있습니다. 실제 구현·권한 정책을 먼저 확인하고, 캐시를 우회하는 검증 호출은 호출 예산과 별도 승인 범위에 포함합니다. 검증 목적으로 상시 권한을 확대하지 않습니다.

성공 판정은 HTTP 상태뿐 아니라 공급자 결과 코드와 예상 응답 구조를 함께 확인합니다. 기록에는 실행 환경·서비스·용도·시각·HTTP 상태·공급자 결과 코드만 남기고 인증값·인증 URL은 남기지 않습니다.

한 서비스·한 용도의 성공을 다른 서비스·batch/realtime·다른 프로젝트·현재 운영 배포의 성공으로 확대하지 않습니다. 서버에서의 검증과 Replit 게시 환경에서의 검증도 구분합니다.

## 8. Replit 연결과 단계별 활성화

### 8-1. 설정 목록

| 이름 | 설정 의미 | 주의 |
|---|---|---|
| RELAY_BASE_URL | https://relay.homenstay.com | 공개 서비스 URL. 홈앤스테이 현재 구성에는 개발·운영 설정에 기재됨 |
| RELAY_TOKEN | realtime 전용 토큰 | 실제 값은 Secrets에만 보관 |
| RELAY_TOKEN_BATCH | batch 전용 토큰 | 홈앤스테이 batch 경로에 필요 |
| RELAY_ENABLED | 정확히 1일 때 전체 중계 허용 | 0·미설정·그 밖의 값은 OFF |
| RELAY_USE_BLDG_HUB | 정확히 1일 때 건축물대장 중계 허용 | RELAY_ENABLED도 1이어야 함 |
| RELAY_USE_RTMS | 정확히 1일 때 지정 실거래 4종 중계 허용 | RELAY_ENABLED도 1이어야 함 |

홈앤스테이의 세 활성화 스위치는 정해진 운영 원칙에 따라 Secrets에서만 관리하고 같은 이름의 일반 설정·실행 명령으로 중복 정의하지 않습니다. URL은 비민감 설정으로 관리할 수 있습니다.

활성화된 서비스의 해당 용도 토큰이 없으면 RELAY_AUTH로 실패합니다. realtime 토큰을 batch에 대신 쓰거나, 중계 실패 시 직접 호출로 자동 우회하지 않습니다.

### 8-2. 홈앤스테이 운영 웹 전환 순서

1. 설정 준비: 개발과 운영 게시 환경을 구분하여 URL 및 필요한 토큰 존재를 확인합니다. 이미 준비된 토큰을 불필요하게 재입력하지 않습니다.
2. 첫 OFF 재게시: 세 스위치를 모두 0 또는 미설정으로 유지하여 게시합니다. 첫 게시 성공 전 활성화 설정을 미리 적용하지 않습니다.
3. 건축HUB 활성화: RELAY_ENABLED=1, RELAY_USE_BLDG_HUB=1로 설정하고 재게시합니다. RELAY_USE_RTMS는 0으로 유지합니다.
4. 운영 확인: 캐시된 정보 열람만이 아니라 실제 건축물대장 요청이 발생하는 승인된 조회로 통신·공급자 결과를 확인합니다.
5. 안정화: 웹 실행 환경의 성공·오류, 공급자 정상 응답, 기존 기능 영향을 확인합니다.
6. 실거래 활성화: 안정화 확인 후 RELAY_USE_RTMS=1을 설정하고 재게시합니다. 승인된 작은 범위부터 서비스·용도별로 확인합니다.
7. 예약 배치 적용: 별도 게시 설정과 batch 토큰을 확인하고, 승인된 기존 예약 작업에 별도로 적용합니다.

같은 실행 환경에서는 서비스 스위치가 realtime/batch 요청에 함께 적용됩니다. 건축HUB realtime만 켜고 같은 환경의 건축HUB batch를 별도 스위치로 끄는 기능은 없습니다. 웹과 별도 예약 배포의 실행 환경을 구분해 단계적으로 전환합니다.

다른 두 프로젝트는 각 프로젝트 코드의 설정·용도·재시도 구현을 먼저 확인한 뒤 같은 단계적 전환 원칙을 적용합니다. 홈앤스테이의 동작을 그대로 보장한다고 해석하지 않습니다.

### 8-3. OFF 복구와 반영 시점

운영 배포 설정에서 스위치를 OFF로 바꾼 뒤 다시 게시하고 새 실행을 확인합니다. 이미 실행 중인 프로세스는 설정 화면 변경을 즉시 다시 읽지 않습니다. 배치도 새 설정으로 시작된 실행부터 적용됩니다.

OFF는 기존 직접 호출 경로로 복귀하는 설정입니다. 기존 직접 연결의 네트워크 장애까지 해결하는 것은 아닙니다. 중계 장애 시 자동 직접 호출 폴백은 없습니다.

### 8-4. Scheduled 배포

Replit 공식 Secrets 문서는 Static을 제외한 모든 배포 유형에서 Secrets를 지원한다고 설명합니다. Scheduled 지원 여부와 해당 예약 배포에 실제 설정이 반영되었는지는 별개입니다.

각 Scheduled 배포의 게시 설정에서 필요한 URL·토큰·스위치를 확인합니다. 개발 또는 웹 앱 설정을 바꿨다는 이유만으로 이미 게시된 예약 배포에 반영됐다고 가정하지 않습니다. 필요한 경우 해당 예약 배포도 재게시하고 새 실행에서 확인합니다. 기존 명령·일정·운영 DB 연결을 임의로 바꾸거나 새 대량 수집을 시작하지 않습니다.

### 8-5. 프로젝트별 원본 이력

아래는 v1의 2026-10-05 기재사항이며 현재 상태를 직접 확인한 표가 아닙니다.

| 프로젝트 | 원본 이력 요약 | 현재 확인할 사항 |
|---|---|---|
| 홈앤스테이 | 중계 코드 반영, 스위치 설정·게시 확인이 남은 것으로 기록 | 실제 게시 버전, 단계별 ON/OFF, 서비스·용도별 운영 검증, 예약 배포 |
| 관리의달인 HP 리뉴얼 | 코드 반영, 46개 테스트·개발 조회 성공으로 기록 | 현재 코드·검사 결과, 게시·스위치, 운영 조회, 저장소 인증값 정리 |

테스트 수는 원본 이력일 뿐 현재 전체 통과 판정이 아닙니다. 홈앤스테이 운영 문서는 실거래 NrgTrade의 과거 서버 허용 추가 및 재점검 성공을 별도로 기록하고 있습니다. 해당 과거 기록을 현재 운영 전체 정상 또는 활성화 완료로 해석하지 않습니다.

```text
relay-admin stats
```

```text
umask 077
cp /etc/relay/config.json /etc/relay/config.json.bak

```

기존 백업을 덮어쓰지 않도록 실제 운영에서는 백업 이름을 구분합니다. v1은 저장 시 자동 반영 및 형식 오류 거부를 설명하지만, 이 동작은 서버 원본 확인이 필요합니다. JSON 문법·설정 스키마·서비스 정책을 검증하고, 잘못된 설정 시 이전 설정 유지 또는 차단 중 어느 동작인지 확인합니다.

## 10. 요청 규칙·오류·재시도·상태 해석

### 10-1. 호출 규칙

v1의 서버 호출 형식은 다음과 같습니다. 실제 서버 정책을 확인한 뒤 사용합니다.

```text
GET https://relay.homenstay.com/v1/fetch?url=<인코딩된 대상 URL>
X-Relay-Token: <해당 용도의 토큰>
X-Relay-Purpose: realtime 또는 batch
```

v1에는 선택 쿼리 force_refresh=0|1, 그 외 쿼리 거부, 성공 헤더 X-Relay-Cache / X-Relay-Fetched-At / X-Relay-Service가 기재되어 있습니다. 홈앤스테이의 현재 일반 전송 함수는 url만 보내며 force_refresh를 사용하지 않습니다.

홈앤스테이에서 확인된 대상 URL 규칙은 HTTPS, 정확한 apis.data.go.kr 호스트, 지정된 서비스 경로, fragment 없음, URL 길이 8192자 이하입니다. '%'와 '..' 차단은 대상 URL의 경로 부분에 적용됩니다. 쿼리의 정상적인 URL 인코딩까지 금지하는 것은 아닙니다.

클라이언트는 중계 응답 리디렉션을 따라가지 않습니다. 서버의 사설 IP 차단·DNS 검증·공급자 리디렉션 차단 등 SSRF 방어는 별도 서버 원본·검사 결과로 확인합니다.

### 10-2. 중계 자체 오류

X-Relay-Error: 1이 있는 응답을 중계 자체 오류로 처리합니다. 헤더가 없는 공급자 오류와 구분합니다. 홈앤스테이는 알려진 code만 사용하며 원격 message와 인증 URL을 예외에 보관하지 않습니다.

| 코드 | HTTP | 의미 | 홈앤스테이 처리 |
|---|---|---|---|
| RELAY_AUTH | 401 | 인증·용도 확인 필요 | 자동 재시도 대상 아님 |
| RELAY_FORBIDDEN | 403 | 허용 목록·정책·요청 확인 필요 | 자동 재시도 대상 아님 |
| RELAY_QUOTA | 429 | 중계 호출 한도 초과 | 공급자 429와 구분, 자동 재시도 대상 아님 |
| CIRCUIT_OPEN | 503 | 서비스 차단 상태 | 자동 재시도 대상 아님, 서버 정책 확인 |
| RELAY_BUSY | 503 | 중계 동시 처리 한도 등 | 기존 호출자 재시도 기능이 있을 때만 재시도 |
| UPSTREAM_TIMEOUT | 504 | 응답 제한시간 초과 | 기존 호출자 재시도 기능이 있을 때만 재시도 |
| UPSTREAM_CONNECT | 502 | 연결 실패 | 기존 호출자 재시도 기능이 있을 때만 재시도 |
| RELAY_INTERNAL | 500 | 중계 내부·설정 오류 | 자동 재시도 대상 아님 |

RELAY_FORBIDDEN을 클라이언트 결함으로 단정하지 않습니다. 서버의 서비스 허용 정책과 토큰 용도도 별도로 확인합니다.

### 10-3. 재시도

홈앤스테이 공통 중계 전송 함수는 요청을 한 번 수행하며 자체 재시도 루프가 없습니다. 재시도 가능한 세 오류는 기존 ConnectTimeout 처리와 호환되는 예외로 전달됩니다. 호출자에 기존 재시도 루프가 있는 경우에만 그 횟수와 대기를 유지합니다.

건축물대장 조회와 건축HUB 수집기에는 기존 재시도 경로가 있지만, 일부 실거래 전송 함수에는 즉시 재시도 루프가 없습니다. 실패분을 나중에 다시 처리하는 배치 기능과 즉시 재시도는 구분합니다. 모든 앱·모든 호출이 자동 재시도된다고 설명하지 않습니다.

공급자 자체 429는 기존 공급자 한도 처리 흐름을 유지합니다. 중계 자체 429는 같은 오류로 재분류하지 않습니다. 다른 프로젝트의 실제 재시도 방식은 각 코드로 별도 확인합니다. v1의 “중계서버는 재시도하지 않음”도 서버 원본 확인이 필요합니다.

### 10-4. 서킷브레이커와 캐시

v1의 기재값은 서비스별 최근 60초 안 5회 실패 시 60초 차단, 성공 시 카운트 초기화, 공급자 결과 코드·totalCount에 따른 실패 판정입니다. 실거래 TTL은 정상 3600초·빈 응답 600초로 기록되어 있습니다.

이 값은 이번 개정에서 서버 구현으로 검증하지 않았습니다. 실제 config·서버 코드·검사 결과와 대조해 확정합니다. 어떤 HTTP 상태·본문이 실패 또는 캐시 대상인지, 빈 결과 코드가 정상 빈 응답인지 공급자별로 확인합니다. v1의 오류 응답 미캐시 설명도 같은 방식으로 확인합니다.

### 10-5. 관리자 중계 상태 해석

홈앤스테이 관리자 상태는 DB 통합 원장이 아니라 로컬 임시 파일 기록입니다. 같은 실행 환경의 웹 워커·로컬 배치 프로세스는 기록을 공유하지만 다른 Autoscale 인스턴스·별도 Scheduled 배포와는 공유하지 않습니다. 임시 저장소가 초기화되면 이력도 사라질 수 있습니다.

마지막 성공은 중계 HTTP 응답 2xx의 시각입니다. 공급자 본문 정상·파싱 성공·DB 적재·전체 배치 완료를 보증하지 않습니다. 최근 오류 코드는 이후 성공해도 남을 수 있으므로 성공 시각과 함께 해석합니다.

관리자 화면 진입과 상태 조회 자체는 공급자 실호출을 하지 않습니다. 화면에 저장된 건물 정보가 표시되었다고 새 중계 통신이 성공한 것은 아닙니다. 예약 배치 상태는 해당 실행 환경과 로그에서 별도로 확인합니다.

| 명령 끝에 ^M 또는 따옴표 오류 | 줄바꿈·붙여넣기·입력 상태 | PC/서버 위치 확인, 한 줄씩 실행 또는 검증된 파일 전송 |
| 새 버전 확인 실패·롤백 | 서비스 로그·파일 및 상위 경로 권한 | relay 접근권한과 실행 옵션 확인, 최소 권한으로 수정 |
| RTMS에서 RELAY_FORBIDDEN | 서버 서비스 허용·토큰 용도·클라이언트 경로 | 양쪽 정책 대조, 권한 우회·자동 직접 폴백 금지 |
| /health는 정상인데 조회 실패 | 인증·허용 목록·공급자 결과·네트워크 | 서비스·용도별로 승인된 실제 요청 확인 |
| 성공 시각 없음 | 실제 요청 발생 여부·환경 구분·임시 기록 | 캐시 표시와 실호출 구분, 해당 환경의 로그 대조 |
| 성공 후 과거 오류가 남음 | 마지막 성공 시각·최근 오류 코드 | 오류 코드만으로 현재 장애 단정 금지 |
| OFF 설정 후에도 기존 경로 사용 | 게시된 설정·프로세스 시작 시점 | 올바른 배포를 재게시하고 새 실행 확인 |
| 예약 배치만 실패 | 예약 배포 설정·batch 토큰·실제 새 실행 | 웹 앱 설정과 구분하여 확인 |

v1의 “지시문 첨부가 본문으로 전달되지 않음”은 이번 검토에서 원인을 확인하지 못한 과거 사례입니다. 첨부 전달 실패로 단정하지 말고 해당 프로젝트·첨부 경로·요청 내용이 정확히 인식됐는지 확인합니다.

## 12. 새 API 추가 절차

1. 공급자의 활용신청·승인·요청 한도·인증 방식·호스트·경로를 확인합니다.
2. 정상 결과 코드와 정상 빈 결과 코드를 구분합니다. 빈 응답을 공급자 장애로 오판하지 않습니다.
3. relay-server의 실제 서비스 스키마·검사에 맞춰 서버 허용 정책을 추가합니다. config.example.json만 수정했다고 운영 반영된 것은 아닙니다.
4. 백업 후 서버 설정을 적용하고, 설치 파일 업데이트가 필요하면 권한 수정과 복구 경로를 확인합니다.
5. 클라이언트에도 새 대상 경로·용도·토큰·스위치 처리를 구현합니다. 서버 허용만으로 홈앤스테이의 현재 허용 목록이 자동 확대되지는 않습니다.
6. OFF 상태로 코드 게시 → 서비스별 단계적 활성화 → 승인된 실호출 검증 → 안정화 순서를 따릅니다.
7. 기존 호출 예산·파싱·반환 구조·DB 연결·예약 일정의 영향과 개인정보 노출을 점검합니다.

## 13. 보안 수칙

- 실제 인증값은 코드·문서·채팅·스크린샷·로그에 남기지 않습니다.
- 서버 토큰 저장은 원문 복구가 불가능한 해시 방식인지 구현으로 확인합니다. 발급 출력도 공유하지 않습니다.
- 공개 저장소와 과거 Git 이력에 인증값·개인정보·내부 DB가 포함되지 않도록 점검합니다.
- 노출된 인증값은 현재 파일에서 지우는 것만으로 해결되지 않습니다. 실제 키·토큰을 교체하고 과거 이력·접근권한을 정리합니다.
- v1에는 다른 프로젝트의 과거 키·고정 비밀번호·세션 쿠키 기록 문제가 기재되어 있습니다. 해당 저장소를 직접 확인하지 않았으므로 이력 조사와 소유자 승인을 거쳐 처리합니다. 무조건 이력을 폐기하거나 새 첫 커밋을 만들라고 지시하지 않습니다.
- 서버 초기·공유·노출 비밀번호는 변경합니다. 전용 관리 계정·SSH 키·최소 접근권한으로 전환하되 콘솔 복구 수단을 먼저 확보합니다.
- v1의 “루트 비밀번호 미변경”은 원본 작성 당시 기록이며 현재 상태는 별도 확인합니다.
- 호스팅 방화벽과 서버 ufw의 실제 규칙, SSH 관리 IP 제한, 보안업데이트·fail2ban 상태를 점검합니다.
- 설정·DB·백업 파일은 필요한 계정만 읽을 수 있도록 제한합니다. 릴리스 권한 수정에서 민감 파일까지 공개하지 않습니다.
- 프로젝트·용도별 토큰을 섞지 않습니다. 노출 의심 시 교체 후 관련 배포의 새 실행에서 적용을 확인합니다.
