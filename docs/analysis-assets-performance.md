# `/api/analysis/assets` 성능 기준선

측정일: 2026-09-07

## 운영 규모 기준선

운영 읽기 전용 복제본에서 12개월·전국·전체 숙박유형의 핵심 정확주소 거래 집계를
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 측정했다.

- `transactions`: 18,612행
- `master_buildings`: 84,104행
- `tourism_stats`: 3,599행
- 실행 시간: 822.054ms
- 계획 시간: 59.126ms
- 정확주소 매칭 결과: 12,171행
- 분석 결과: 393개 건물
- 공유 버퍼: hit 110,697, read 1,552
- 주요 병목: 거래 원장 순차 스캔 뒤 건물 주소키 조인과 중복 주소 anti-join

전체 공개 API의 기존 개발 기준선은 요청당 약 4~6초였다. 이 차이에는 관광 월별
정규화·기간 집계, 필터 옵션과 건물 집계, JSON 응답 조립 시간이 포함된다.

## 적용 방식과 목표

6·12·24개월별 관광 집계와 기간·지역·숙박유형별 정확주소 거래 집계를 PostgreSQL
JSONB 캐시에 저장한다. 캐시는 프로세스 메모리가 아니므로 여러 Gunicorn 워커가
공유한다.

`tourism_stats`, `transactions`, `master_buildings`의 INSERT/UPDATE/DELETE/TRUNCATE
문장 트리거가 원장 버전을 올리고 관련 캐시를 삭제한다. 캐시 행에도 조회 당시 원장
버전을 기록하므로, 원장 갱신과 캐시 생성이 겹쳐 이전 스냅샷이 늦게 저장돼도 다음
요청에서 재사용되지 않는다.

거래 기간은 PostgreSQL `CURRENT_DATE` 기준 이동 구간이므로 거래 캐시 키에 DB 날짜도
포함한다. 원장 변경이 없는 자정 경계에서도 전날 집계를 재사용하지 않는다.

- cold miss: 기존 산식과 같은 결과를 계산하고 저장한다.
- warm hit 목표: 고비용 원장 집계를 실행하지 않고 캐시 읽기와 응답 조립만 수행한다.
- 무결성: 6·12·24개월과 관광수요 지수·실제 동기간 증감률 모두 같은 캐시 원자료를
  사용하며, 축 선택은 캐시 이후의 기준선·사분면 계산에만 영향을 준다.
