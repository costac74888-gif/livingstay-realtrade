# 홈앤스테이 데이터 수집·동기화 운영매뉴얼

**문서 ID:** RUN-SYNC-001  
**버전:** V.01.0  
**기준일:** 2026-09-04  
**상태:** 현행  
**대상:** 데이터 운영자, 승인 관리자, 장애 대응 담당자  
**상위 정책:** `DATA_COLLECTION_GOVERNANCE_OPERATIONS_POLICY_V03_0_2026-09-04.md`

## 1. 목적과 적용 범위

이 문서는 운영자가 수집기 코드를 읽지 않고도 공공 API, 정부 CSV, 건축물대장,
실거래, 숙박·야영장 원본을 안전하게 수집·검증·승격·재시도하도록 순서와
중단 기준을 정한다.

이 문서가 다루는 범위:

1. 원본별 책임, 수집기, 주기와 관찰 지점
2. 인증키와 일일 호출 한도 관리
3. 정기 동기화의 정상 실행, 부분 실패, 중단과 재개
4. 정부 숙박 CSV 8종의 개발 staging, 검토, 승인과 운영 승격
5. 정부 야영장 CSV와 고캠핑 API의 역할 분리 및 교차 연결
6. 장애 유형별 확인 지표, 중단 조건과 복구 후 검증

다음은 이 문서의 범위가 아니다.

- 공개 통계 산식 상세
- 일반 사용자 화면 사용법
- 수집기 코드 또는 스키마 변경 절차

---

## 2. 운영자가 먼저 지켜야 할 원칙

1. **대상 DB를 먼저 확인한다.** 개발 staging과 운영 반영을 같은 작업으로
   취급하지 않는다.
2. **Publish는 데이터를 옮기지 않는다.** 코드 배포와 데이터 승격은 별도다.
3. **확인된 한도의 80%만 정기 작업에 배정한다.** 한도를 추정해서 늘리지 않는다.
4. **같은 인증키·공급자 한도를 공유하면 직렬 실행한다.** 단, 코드에 서로 침범할
   수 없는 별도 배정량과 상태 키가 명시된 stage는 그 분리 계약을 따른다.
5. **완료 stage는 다시 돌리지 않는다.** 실패·보류·취소 stage만 재개한다.
6. **체크포인트와 호출량 카운터를 임의로 지우지 않는다.**
7. **정부 CSV는 개발에서 검증·승인한 뒤 dry-run을 거쳐 운영에 반영한다.**
8. **원본 행과 비활성 이력은 삭제하지 않는다.** 공개 여부와 원본 보존은 별개다.
9. **승인 원본의 해시·행 수·계보가 달라지면 승격을 중단한다.**
10. **비밀값과 개인정보를 문서, 채팅, 이슈, 로그에 복사하지 않는다.**

## 3. 역할과 책임

| 역할 | 책임 | 해서는 안 되는 일 |
|---|---|---|
| 예약 워크플로 | 정해진 stage 실행, 상태·heartbeat·결과 기록 | 실패를 성공으로 표시 |
| 수집기 | 외부 요청, 파싱, UPSERT, 체크포인트 저장 | 공급자 한도를 우회 |
| 개발 데이터 운영자 | CSV 원본 등록, staging 검증, review 해결 | 개발 ID를 운영 ID로 복사 |
| 승인 관리자 | staging 변경분 승인, 수동승격일 때 dry-run 결과 추가 승인 | 미해결 review가 있는 승격 승인 |
| 운영 담당자 | 운영 반영, 상태·표본·캐시 확인 | 대상 DB 미확인 상태로 실제반영 |
| 장애 대응 담당자 | 원인 분류, 안전 중단, 체크포인트 재개 | commit 확인 없이 반복 실행 |

### 4.2 별도 원본

| 원본 | 책임 | 처리 경로 | 주기 |
|---|---|---|---|
| 정부 숙박 CSV 8종 | 법정 인허가 원장 snapshot | 개발 staging → 검토·승인 → manifest → 운영 승격 | 새 공표본 확보 시 |
| 일반·자동차야영장 정부 CSV | 법정 업종·허가·상태 원장 | 위 8종 경로에 포함 | 새 공표본 확보 시 |
| 고캠핑 `basedList` | 운영 시설 설명·상태·유형별 사이트 수 보강 | `sync_lodgings.py --camping` | 매일 |
| 전국 건축HUB 전수 스캔 | 건물 마스터·표제부 보강 | 별도 장시간 workflow | 필요 시/체크포인트 재개 |
| 장기 실거래 backfill | 최근분 밖의 과거 거래 | 별도 backfill·retry workflow | 필요 시 |

### 4.3 현재 예약 워크플로 경계

1. `최근 실거래 자동 동기화`, `농어촌민박 자동 동기화`,
   `한옥체험업 자동 동기화`는 독립 stage로 실행한다.
2. `정기 API 통합 동기화`는 위 독립 stage를 제외한 나머지를 실행한다.
3. 동일 stage를 관리자 수동 실행과 예약 실행으로 겹쳐 돌리지 않는다.
4. 장시간 작업은 Shell의 임시 백그라운드 프로세스가 아니라 지정된 Replit
   workflow로 실행한다.

## 5. 인증키·한도·병렬 실행 규칙

### 5.1 인증키 관리

1. 키는 Replit Secrets에만 저장한다.
2. 문서에는 환경변수 이름만 기록하고 실제 값은 기록하지 않는다.
3. URL, 예외, 외부 응답을 로그에 남기기 전에 인증 쿼리값과 URL 인코딩된 값까지
   마스킹한다.
4. 키 오류가 발생하면 값을 로그에 출력해 확인하지 말고, secret 존재·권한·공급자
   응답코드만 확인한다.
5. 키 교체 후에는 공유 키를 쓰는 모든 stage의 상태를 함께 확인한다.

### 5.2 정기 배정 기준

모든 날짜 경계는 한국시간(KST)을 사용한다.

| 공급자/버킷 | 확인된 일일 한도 | 정기 soft cap | 공유 원칙 |
|---|---:|---:|---|
| 국토부 실거래 | 10,000 | 8,000 | 관련 거래 stage가 공급자 카운터 공유 |
| 건축HUB | 10,000 | 8,000 | 건축물대장·인허가 직렬 |
| 행안부 숙박 | 10,000 | 8,000 | 일반·생활숙박 |
| 고캠핑 | 1,000 | 800 | 캠핑 전용 체크포인트 |
| 공인중개사 | 1,000 | 800 | 해당 공급자 내 직렬 |
| 소상공인 상가정보 | 10,000 | 8,000 | 실시간 1,500·수동 500 별도 예약 |
| 농어촌민박 | 5,000 | 4,000 | 공유 10,000 중 절반을 독립 배정 |
| 한옥체험업 | 5,000 | 4,000 | 공유 10,000 중 절반을 독립 배정 |
| 관광펜션 | 2,000 | 1,600 | 별도 버킷 |
| 카카오 건물·중개업소 주소검색 | 확인 필요 | 확인 필요 | 앱별 쿼터 확인 전 수치 추정 금지 |

코드의 현재 설정이 바뀔 수 있으므로 실행 전 `scheduled_sync.py --list`와 관리자
상태를 권위로 삼는다. 표와 코드가 다르면 실행하지 말고 문서 또는 설정을 먼저
일치시킨다.

### 5.3 병렬·직렬 판단

1. 서로 다른 API 키·공급자 버킷이고 DB writer 잠금이 다르면 병렬 실행할 수 있다.
2. 같은 공급자 일일 카운터를 공유하면 직렬 실행한다.
3. 건축HUB 표제부와 인허가는 반드시 직렬 실행한다.
4. 기존 숙박 직접 수집과 숙박 manifest 승격은 잠금으로 직렬화한다.
5. 같은 stage의 예약·수동 실행은 금지한다.
6. 농어촌민박과 한옥은 공유 총량을 각각 5,000회로 미리 분할하고 독립 상태 키를
   사용하므로 현재 독립 workflow가 병렬 실행될 수 있다. 한쪽의 남은 배정량을
   다른 쪽에 임의로 넘기지 않는다.
7. 카카오 주소검색은 확인된 정기 한도가 없으므로 숫자를 추정하거나 병렬도를
   늘리지 않는다.
8. DB 연결 여유가 불명확하거나 사용자 요청 지연이 증가하면 병렬도를 늘리지 않는다.

### 5.4 한도 소진 시

1. 현재 KST 날짜와 공급자·정기 카운터를 확인한다.
2. soft cap 도달은 정상 중단으로 보고 강행하지 않는다.
3. HTTP 429가 발생하면 같은 키를 쓰는 stage를 모두 중단한다.
4. 체크포인트를 보존한다.
5. 다음 KST 날짜에 저장 위치부터 재개한다.
6. `--dry-run`도 실제 API를 호출하면 한도를 소모한다.
7. 호출량 카운터를 수동 삭제하거나 낮추지 않는다.

## 6. 정기 동기화 표준 절차

### 6.1 실행 전

1. 실행 대상이 운영 DB인지 확인한다.
2. `python -u scheduled_sync.py --list`로 stage와 주기를 확인한다.
3. 관리자 동기화 상태에서 같은 stage가 `running`인지 확인한다.
4. 마지막 heartbeat가 5분 이내인 `running`은 살아 있는 실행으로 간주한다.
5. 공급자별 오늘 호출량과 남은 soft cap을 확인한다.
6. 이전 실행의 `failed`, `deferred`, `cancelled`, `partial` stage를 확인한다.
7. 운영 시간대 사용자 요청 지연과 DB 잠금 여부를 확인한다.

### 6.2 정상 예약 실행

1. 지정된 예약 workflow가 통합 실행을 시작한다.
2. 스케줄러는 run ID를 만들고 stage별 상태를 기록한다.
3. 각 자식 수집기는 별도 run ID와 상태 키를 사용한다.
4. 약 30초마다 heartbeat를 갱신한다.
5. 수집기는 안전한 처리 단위마다 commit과 체크포인트를 저장한다.
6. 성공 stage는 `done`, 한도·선행작업 때문에 미룬 stage는 `deferred`,
   오류 stage는 `failed`로 기록한다.
7. 전체 종료 후 성공·실패·보류·취소 stage와 마지막 지표를 확인한다.

### 6.3 수동 전체 실행

예약 시간을 기다릴 수 없는 명확한 사유가 있을 때만 **관리자 데이터 동기화의
전체 정기 동기화 실행 기능**을 사용한다. 관리자 기능은 먼저 run ID와 수동 실행
소유권을 기록한 뒤 자식 명령을 시작한다.

`python -u scheduled_sync.py --source manual`을 일반 Shell에서 단독 실행하지
않는다. 이 명령은 관리자 기능이 사전에 기록한 같은 run ID가 없으면 소유권 상실로
종료하도록 설계돼 있다. 이미 완료된 정기 실행을 단순 확인 목적으로 다시 실행하지
않는다.

### 6.4 특정 stage 실행

1. 관리자 데이터 동기화에서 해당 stage의 수동 실행 기능을 사용한다.
2. 해당 stage가 다른 실행에 포함되지 않았는지 확인한다.
3. 공급자 공유 버킷의 다른 stage가 실행 중이지 않은지 확인한다.
4. 관리자 기능이 발급한 run ID와 child 상태 키가 같은 실행을 가리키는지 확인한다.
5. 실행 후 해당 stage 상태와 전체 상태를 함께 확인한다.

일반 Shell에서 `--stage ... --source manual`만 조합해 실행하지 않는다. run ID
claim 없이 실행하면 안전장치가 작업을 거부한다.

### 6.5 실패 stage만 재시도

1. 실패 원인이 해소됐는지 먼저 확인한다.
2. 관리자 데이터 동기화의 **실패 단계 재시도** 기능을 사용한다.
3. 이전 완료 stage가 보존되는지 확인한다.
4. 실패·보류·취소 stage만 다시 실행되는지 확인한다.
5. 재시도 후 새 run ID, heartbeat, 종료 상태와 지표 변화를 기록한다.

재시도도 관리자 기능이 수동 run ID 소유권을 먼저 기록한다. 일반 Shell의
`--retry-failures --source manual` 단독 실행은 표준 운영 절차가 아니다.

## 7. 체크포인트·부분 실패·중단 복구

### 7.1 체크포인트 해석

| 수집기 | 재개 단위 | 운영 판단 |
|---|---|---|
| 실거래 | 월 및 실패 queue | 실패 월만 rollback·재적재 |
| 건축HUB | 법정동/조회 index | 마지막 저장 index 다음부터 재개 |
| 일반·생활숙박 | API page | 대상 업태 계약이 같을 때 다음 page부터 재개 |
| 고캠핑 | API page | 별도 캠핑 체크포인트에서 재개 |
| 농어촌·한옥·펜션 | source별 진행상태 | source 상태 키별 재개 |
| 통합 스케줄러 | stage | 완료 stage 보존, 실패 stage 재실행 |

숙박 대상 업태가 변경되면 과거 page 체크포인트를 그대로 쓰지 않는다. 수집기가
대상 계약 차이를 감지해 처음부터 다시 시작하도록 두고, 운영자가 임의 page를
만들지 않는다.

### 7.2 정상 중단

1. 가능하면 workflow의 정상 중지 또는 SIGTERM을 사용한다.
2. 스케줄러는 활성 자식에게 종료를 전달한다.
3. 자식은 안전 체크포인트에서 멈춘다.
4. 상태가 `cancelled`, `retryable=true`인지 확인한다.
5. 마지막 heartbeat, commit, 체크포인트 시각을 기록한다.
6. 원인이 해소된 후 관리자 데이터 동기화의 **실패 단계 재시도** 기능으로
   재개한다.

### 7.3 비정상 중단

1. `running` 상태의 마지막 heartbeat가 5분 이상 오래됐는지 확인한다.
2. 실제 프로세스가 남아 있는지 확인한다.
3. DB 잠금과 run ID 소유권을 확인한다.
4. 마지막 commit과 체크포인트를 확인한다.
5. 살아 있는 실행이 없을 때만 stale 실행을 실패로 회수하고 재시도한다.
6. 수집기의 UPSERT·월 단위 rollback·manifest 멱등 계약을 이용해 작은 단위로
   다시 실행한다.

### 7.4 금지되는 복구

- 승인 없이 `--reset` 실행
- `app_meta`의 체크포인트·호출량 직접 삭제 또는 조작
- 프로세스 확인 없이 stale로 단정하고 중복 실행
- 부분 commit 여부 확인 없이 처음부터 대량 재실행
- 실패 queue를 삭제해 오류를 숨김
- 새 run ID가 소유권을 가진 상태에서 과거 run의 상태 덮어쓰기

## 8. 원본별 실행·복구 절차

### 8.1 실거래

1. 최근 자동 동기화는 최근 3개월을 대상으로 한다.
2. 요청 전 공급자·정기 카운터가 원자적으로 예약되는지 상태에서 확인한다.
3. 429 또는 부분 실패 시 실패한 월과 attempts를 확인한다.
4. 성공한 월을 다시 API 호출하지 않고 실패 월만 retry queue로 처리한다.
5. 월 적재 중 DB 오류가 나면 그 월을 rollback하고 같은 월을 멱등 재적재한다.
6. 복구 후 거래 전체 건수만 보지 말고 실패 queue 감소, 최신 거래월, 표본 중복을
   확인한다.

장기 backfill은 지정 workflow를 사용하며 정기 최근분 수집과 동시에 같은 버킷을
소진하지 않는다.

### 8.2 건축물대장·인허가

1. 월·수·금은 건축물대장, 화·목·토는 인허가 일정을 지킨다.
2. 실행 전에 건축HUB 공유 호출량과 다른 writer 실행을 확인한다.
3. 건축물대장은 진행 index와 마지막 성공 법정동을 확인한다.
4. soft cap 도달 시 체크포인트를 유지하고 다음 허용일에 재개한다.
5. 응답이 비어도 HTTP 성공만으로 완료 처리하지 말고 실제 응답 건수와 진행 index를
   함께 확인한다.
6. 복구 후 신규·갱신 건물, 좌표·표제부 보강 대상, 실패 법정동을 표본 확인한다.

### 8.3 일반·생활숙박 API

1. 행안부 API에는 서버측 업태 필터가 없으므로 전체 page를 순회한다.
2. 응답은 요청 행 수와 무관하게 100행 단위일 수 있으므로 실제 응답 길이로 종료를
   판단한다.
3. 서비스가 허용한 업태만 저장하되 원문 업태를 보존한다.
4. 관리번호 기준 UPSERT 후 page 체크포인트를 저장한다.
5. 한도 도달, 429, DB 실패 시 다음 page를 임의로 넘기지 않는다.
6. 완료 후 마지막 동기화 시각, 처리 건수, 신규·변경·오류, 통계 무효화 신호를
   확인한다.

### 8.4 농어촌민박·한옥·관광펜션

1. source별 상태 키와 체크포인트를 독립적으로 본다.
2. 한 source의 실패를 다른 source의 성공으로 덮지 않는다.
3. 농어촌민박과 한옥은 공유 총량을 절반씩 나눈 독립 배정량 안에서 병렬 실행할 수
   있다. 한 source의 여유분을 다른 source에 임의로 더하지 않는다.
4. 관광펜션은 별도 배정량과 상태 키를 따른다.
5. 누락 필드는 기존 값을 지우라는 뜻으로 해석하지 않는다.
6. 복구 후 source별 원장 수, 신규·변경·상태변경, 주소 미연결을 확인한다.

### 8.5 고캠핑 API

1. `contentId`, 시설명, 주소, `manageSttus`, 수정시각을 원문 기준으로 읽는다.
2. 사이트 수는 일반·자동차·글램핑·카라반 네 종류로 보존한다.
3. 카라반 수는 관련 두 원본 필드의 합으로 처리한다.
4. 음수·잘못된 수량은 확정 수량으로 사용하지 않는다.
5. dry-run도 실제 호출량을 소모하므로 시험 횟수를 제한한다.
6. 응답 구조가 안전하지 않으면 체크포인트를 전진시키지 않고 중단한다.
7. 완료 후 API 전체건수가 아니라 활성 원장, 중복 제거 시설, 연결 건물과 사이트
   수를 각각 확인한다.

## 9. 정부 숙박 CSV 8종 운영 절차

### 9.1 8종 범위

1. 관광숙박업
2. 관광펜션업
3. 농어촌민박업
4. 숙박업
5. 외국인관광도시민박업
6. 일반야영장업
7. 자동차야영장업
8. 한옥체험업

전문휴양업은 현행 범위에서 제외한다.

### 9.2 1단계 — 원본 접수

1. 출처, 원본 종류, 기준일, 파일명과 SHA-256을 기록한다.
2. 8종이 모두 있는지 확인한다.
3. 압축을 푼 뒤 파일별 인코딩·헤더·행 수를 확인한다.
4. 파일을 임의 수정하지 않는다. 보정이 필요하면 원문을 보존하고 해석 규칙으로
   처리한다.
5. 원본에 비밀값이나 업무 목적과 무관한 개인정보가 섞였는지 확인한다.

### 9.3 2단계 — 개발 DB 확인

1. staging은 개발 DB에서만 수행한다.
2. 환경 이름이나 URL 문자열이 아니라 실제 개발·운영 DB 지문을 비교한다.
3. 두 DB가 같거나 확인할 수 없으면 즉시 중단한다.
4. 운영 DB는 기준선 비교를 위해 읽기 전용으로만 사용한다.

### 9.4 3단계 — inspect와 staging

1. 먼저 DB를 변경하지 않는 inspect로 파싱 결과를 확인한다.
2. 원본 종류, 기준일, 파일 SHA 조합을 배치 키로 사용한다.
3. 같은 snapshot 재업로드는 기존 배치를 재사용해야 한다.
4. 원본 파일 bytes와 각 행의 원문 JSON을 보존한다.
5. 1,000행 등 제한된 batch 단위로 적재해 장시간 단일 transaction을 피한다.

공통 CSV staging을 `import_camping_lodging.py` 같은 개별 importer로 대체하지
않는다. 공통 staging은 데이터 계약과 DB 지문 검사를 거쳐야 한다.

### 9.5 4단계 — 자동 검증

각 원본에서 다음을 확인한다.

1. 관리번호 또는 공적 원장 식별자
2. 허용된 원본 종류와 업태
3. 영업상태와 상태 버킷
4. 도로명·지번 주소 및 정규화 결과
5. 객실수와 캠핑 사이트수의 숫자 형식·의미
6. snapshot 내부 중복
7. 기존 원장 대비 `new`, `changed`, `status_change`, `unchanged`
8. 원본 간 관리번호 충돌

누락·미분류·알 수 없는 상태·중복·충돌은 임의 보정하지 않고
`review_required`로 보존한다.

### 9.6 5단계 — 주소·건물 매칭

1. 운영에 같은 허가번호와 유효한 기존 연결이 있으면 우선 보존한다.
2. 신규 허가 또는 실제 주소 변경분만 재매칭한다.
3. 도로명 고유 일치를 우선하고 후보가 없을 때 지번 고유 일치를 사용한다.
4. 도로명과 지번이 서로 다른 건물을 가리키면 보류한다.
5. 복수 후보, 주소 충돌, 주소 없음은 자동 연결하지 않는다.
6. 사업장명 유사도로 주소 충돌을 임의 해결하지 않는다.
7. 개발 매칭률을 운영 매칭률로 해석하지 않는다.
8. 신규 건물 후보는 공적 건축물 확인 전 자동 생성하지 않는다.

### 9.7 6단계 — 관리자 검토와 승인 payload

1. 원문과 정규화 값, 기존 운영 값과 변경값을 함께 본다.
2. 상태변경, 업태·분류, 수량 이상치, 주소 후보를 검토한다.
3. 미해결 review가 0건인지 확인한다.
4. 검증 통과 변경분만 승인 payload로 고정한다.
5. 승인자와 승인시각을 기록한다.
6. 승인 후 원본 해시·행 수·payload가 바뀌면 승인을 재사용하지 않는다.
7. 부분 검토 해결 시 남은 검토행을 자식 manifest에서 누락하지 않는다.

### 9.8 7단계 — 운영 기준선 manifest와 dry-run

현재 옵션을 먼저 확인한다.

```bash
python build_lodging_production_manifest.py --help
python apply_lodging_promotion.py --help
```

대표 절차:

```bash
python build_lodging_production_manifest.py \
  --created-by <ADMIN_ID> \
  --output <MANIFEST_JSON>

python apply_lodging_promotion.py <MANIFEST_ID>
```

dry-run에서 다음을 모두 확인한다.

1. 최신 8종 staging 존재
2. 원본 최신성 기준 충족
3. 미해결 review 0건
4. 변경분이 있는 원본의 승인 완료
5. 신규·수정·상태변경·동일·보류 건수
6. 기존 운영 건물 연결 보존
7. 신규 연결·신규 건물 후보·복수 후보·충돌 수
8. 객실수 공란이 기존 운영 값을 지우지 않는지
9. staging 원본 지문과 운영 기준선이 manifest 생성 시점과 같은지

한 항목이라도 확인되지 않으면 실제반영하지 않는다.

### 9.9 8단계 — 정기 자동승격과 수동 실제반영

#### 9.9.1 정기 자동승격

정기 통합 stage의 `lodging_promotion`은 `apply_lodging_promotion.py --scheduled`
를 실행한다. 이 경로는 단순 점검이 아니라 다음을 연속 수행한다.

1. 최신 8종 staging의 상태·최신성·미해결 review·변경분 승인을 검사한다.
2. 조건이 하나라도 맞지 않으면 `blocked`로 기록하고 운영 반영 없이 실패한다.
3. 조건이 모두 맞으면 운영 기준선 manifest를 만든다.
4. draft manifest를 자동 승인하고 dry-run을 수행한다.
5. 같은 실행에서 운영 반영과 병행 비교까지 수행한다.
6. 비교에 중대 회귀 또는 화면 차단 사유가 있으면 성공으로 보고하지 않는다.

따라서 운영자는 정기 stage가 돌기 전에 staging 검토와 변경분 승인이 끝나면
자동 운영 반영까지 이어질 수 있음을 전제로 승인해야 한다. “승인 후 나중에 별도
최종 버튼을 누른다”는 가정으로 변경분을 승인하지 않는다.

#### 9.9.2 예외적 수동 실제반영

승인된 dry-run의 실행번호를 사용한다.

```bash
python apply_lodging_promotion.py <MANIFEST_ID> \
  --apply \
  --confirm-run-id <DRY_RUN_ID>
```

수동 경로는 자동승격 차단 원인을 조사하거나 승인된 특정 manifest를 운영자가
명시적으로 복구할 때 사용한다.

1. 정기 `lodging_promotion`과 기존 숙박 수집기가 실행 중이지 않은지 확인한다.
2. 승격 잠금과 staging 원본 공유잠금을 획득한다.
3. 승인 payload 행 수·hash와 source snapshot을 다시 검증한다.
4. 운영 기준선이 바뀌지 않았는지 확인한다.
5. 운영 transaction과 감사 표식을 기록한다.
6. 통계 무효화 marker를 같은 반영 흐름에서 기록한다.
7. 병행 비교가 차단 사유를 내면 성공으로 종료하지 않는다.

### 9.10 9단계 — 반영 후 검증

1. 정기 자동승격인지 수동 복구인지와 run ID를 기록한다.
2. manifest 상태와 운영 감사 표식을 확인한다.
3. 원본별 신규·수정·상태변경 건수를 dry-run과 비교한다.
4. 기존 연결이 보존됐는지 표본 확인한다.
5. 신규 건물·미연결·충돌 표본을 확인한다.
6. 객실수 공란과 사이트수가 기존 값을 잘못 덮지 않았는지 확인한다.
7. 통계 무효화 처리와 갱신 시각을 확인한다.
8. 관리자 목록, 지도, 건물 상세에서 정상영업 표본을 확인한다.
9. 비활성 원문과 내부 검토 정보가 공개 응답에 나오지 않는지 확인한다.

| 구분 | 정부 일반·자동차야영장 CSV | 고캠핑 API |
|---|---|---|
| 주 책임 | 법정 업종·허가·영업상태 원장 | 관광 시설 정보와 운영·사이트 세부 보강 |
| 식별자 | 관할기관 코드 + 관리번호 기반 | `contentId` 기반 |
| 사이트 수 | 단일 사이트 수가 있을 수 있음 | 일반·자동차·글램핑·카라반 유형별 수 |
| 원본 갱신 | 새 snapshot 접수·승인 | 매일 API 동기화 |
| 운영 반영 | 8종 staging·manifest 승격 | 체크포인트 API UPSERT |
| 우선 원칙 | 법정 신고 존재·업태·상태 | 시설 설명·유형별 사이트 정보 |

### 10.1 교차 원본 연결 원칙

1. 서로 다른 식별자 체계를 억지로 같은 키로 만들지 않는다.
2. 숫자 `contentId`가 확인된 고캠핑 행만 공식 고캠핑 식별자로 취급한다.
3. 관할기관 코드와 관리번호를 `contentId`로 추정하지 않는다.
4. 원본별 permit key와 원문 JSON을 각각 보존한다.
5. 주소, 정규화 상호, 공적 허가정보를 보조 근거로 같은 시설 후보를 찾는다.
6. 주소 충돌·복수 후보는 자동 병합하지 않는다.
7. 동일 시설의 법정 허가 원장은 삭제하지 않고 대표 시설·건물 연결만 관리한다.
8. 캠핑 시설수는 활성 원장을 교차 원본 중복 제거한 값이며 고캠핑 응답 전체건수가
   아니다.
9. 객실수와 캠핑 사이트수를 서로 대체하지 않는다.
10. 사이트 유형이 확인되지 않으면 `unknown`을 보존하고 확정 혼합형으로 만들지 않는다.

## 11. 원본 변경 대응

### 11.1 API 응답 구조 변경

1. 필수 key 누락, 목록 구조 변화, 비정상 페이지 크기를 감지하면 중단한다.
2. 체크포인트를 전진시키지 않는다.
3. 오류 응답에서 인증값을 마스킹한다.
4. 마지막 정상 응답과 새 응답의 field 목록·자료형을 비교한다.
5. 파서와 검증 계약이 갱신되기 전 운영 반영을 재개하지 않는다.
6. dry-run도 한도를 소모하는 API는 최소 표본으로 검증한다.

### 11.2 정부 CSV 형식 변경

1. 새 파일을 기존 파일 위에 덮어쓰지 않는다.
2. 기준일과 SHA-256이 다른 새 batch로 접수한다.
3. 헤더 변경, 인코딩, 행 수 증감, 업태·상태 새 값을 확인한다.
4. 미제공 필드를 기존 값 삭제로 해석하지 않는다.
5. 확인된 표기 변형은 원문을 유지하고 분류 규칙에서만 정규화한다.
6. 승인 후 파일이 바뀌면 새 approval과 manifest를 만든다.

### 11.3 대량 증감

다음은 즉시 중단 조건이다.

- 원본 행 수의 설명되지 않는 급증·급감
- 정상 신고의 대량 비활성 전환
- 관리번호 충돌 증가
- 주소 미연결·복수 후보·충돌 급증
- 객실수 또는 사이트수 합계의 비현실적 변화
- 기존 운영 연결의 대량 해제

원인을 원본 공표 변화, 파서 변화, 기준선 차이로 나눠 설명할 수 있고 관리자 승인을
받기 전까지 실제반영하지 않는다.

SELECT key, updated_at, value
FROM app_meta
WHERE key LIKE 'scheduled_sync_status%'
   OR key IN (
       'lodging_sync_progress',
       'camping_sync_progress',
       'lodging_promotion_status',
       'master_stats_invalidation'

4. 오늘 호출량과 soft cap

python -u scheduled_sync.py --help

# 수동 전체·특정 stage·실패 stage 재개

python build_lodging_production_manifest.py \
  --created-by <ADMIN_ID> \

## 16. 운영 완료의 정의

수집·동기화 작업은 다음이 모두 충족돼야 완료다.

1. 프로세스가 정상 종료됐다.
2. 상태와 heartbeat가 최종 상태로 기록됐다.
3. 체크포인트와 호출량이 실제 실행과 일치한다.
4. 실패 queue와 review가 설명 가능한 상태다.
5. dry-run과 실제 쓰기 건수가 허용 범위 안이다.
6. 원본·승인·manifest·감사 계보가 보존됐다.
7. 통계 무효화와 갱신이 완료됐다.
8. 운영 관리자 및 공개 표본에서 누락·중복·비활성 노출이 없다.
9. 비밀값과 개인정보가 로그·문서에 남지 않았다.
