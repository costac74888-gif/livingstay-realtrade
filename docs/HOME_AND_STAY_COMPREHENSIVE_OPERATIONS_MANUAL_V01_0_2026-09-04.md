## 1. 문서 목적과 사용법

### 1.1 목적과 적용 범위

이 문서는 데이터 수집, 검증, 운영 승격, 통계, 공개, 개인정보와 사진 정책을 한 번호 체계로 연결한다. 운영자는 이 파일과 문서대장만으로 실행 전제, 중단·복구 기준과 상세 근거 문서를 찾을 수 있어야 한다.

### 1.2 권위와 충돌 해결

1. 법령·동의·계약 중 더 엄격한 기준
2. 공개·개인정보는 제8장과 POL-EXPOSURE-001
3. 데이터 수집·승격은 제2~6장과 POL-DATA-003
4. 통계는 제7장, 사진은 제9장
5. 실제 코드·워크플로·테스트
6. 보존된 개별 매뉴얼과 역사자료

문서와 코드가 다르면 공개 확대나 운영 반영을 중단하고 먼저 일치시킨다.

### 1.3 문서 상태와 책임

`현행`은 현재 판단 기준, `보조`는 현행을 보완하는 자료, `대체됨`은 권위를 승계한 문서가 있는 자료, `역사자료`는 당시 증거다. 운영자는 실행 증거를, 승인자는 dry-run과 중단조건 승인을, 문서 관리자는 원본·대장·배포본의 버전을 책임진다.

## 2. 공통 원칙과 환경 경계

### 2.1 핵심 원칙

- 운영 DB 직접 반영을 최소화하고 신규 대량 원본은 개발 staging에서 검증한다.
- Publish는 코드만 배포하며 개발 데이터를 운영으로 옮기지 않는다.
- 확인 불가, 승인 원본 변경, 미해결 검토 또는 기준선 불일치 시 실패로 닫는다.
- 작업은 멱등이어야 하며 run ID, heartbeat, commit과 체크포인트를 남긴다.
- 비밀값·개인정보·원본 IP를 문서와 로그에 기록하지 않는다.

### 2.2 개발·운영 경계

| 구분 | 개발 | 운영 |
|---|---|---|
| 목적 | staging, 검증, 승인, 시험 | 실제 서비스, 예약 수집, 승인 반영 |
| DB 판단 | 실제 DB 지문으로 확인 | 독립 연결의 실제 DB 지문으로 확인 |
| 데이터 이동 | 자동 이동 없음 | 승인 manifest 또는 명시적 병합으로만 수신 |
| 실패 처리 | 원본·검토 상태 보존 | 사용자 영향 차단, commit 확인 후 복구 |

## 3. 데이터 원본과 공통 계약

원본, 정규화 값, 서비스 분류와 공개 projection을 분리한다. 관리번호·공적 식별키별 원장 이력은 보존하고, 도로명 우선·지번 보조로 주소를 연결한다. 건축물 용도와 영업신고 분류는 서로 덮어쓰지 않는다.

### 3.2 정부 숙박 CSV 8종

관광숙박업, 관광펜션업, 농어촌민박업, 숙박업, 외국인관광도시민박업, 일반야영장업, 자동차야영장업, 한옥체험업을 포함한다. 전문휴양업은 제외한다.

### 3.3 상태 처리

| 내부 상태 | 원장 | 활성 통계 | 개별 공개 | 관리자 |

| 영업·정상 | 보존 | 포함 | 승인 최소정보 | 가능 |
| 휴업 | 보존 | 제외 | 상태·날짜 금지 | 업무상 가능 |

## 4. 수집·동기화 운영

### 4.1 표준 흐름

외부 원본 → 원본 지문 기록 → 수집·staging → 형식·중복·상태 검증 → 주소 매칭 → 검토·승인 → dry-run → 운영 반영 → 통계 무효화 → 공개 표본 확인 순서다.

### 4.2 실행 규칙

- 현재 stage와 옵션은 실행 직전 `python -u scheduled_sync.py --list`로 확인한다.
- 확인된 공급자 한도의 80% 이내만 정기 배정한다.
- 같은 공급자·서비스키·writer를 공유하는 작업은 직렬 실행한다.
- 완료 stage는 보존하고 failed, deferred, cancelled만 재시도한다.
- 장시간 작업은 Shell 임시 백그라운드가 아니라 지정 workflow를 사용한다.

### 4.3 체크포인트와 복구

실거래는 실패 월, 건축HUB는 조회 index, API는 page, 통합 스케줄러는 stage 단위로 재개한다. heartbeat가 5분 이상 멈추고 실제 프로세스가 없을 때만 stale로 회수한다. 체크포인트·호출량을 임의 삭제하거나 commit 확인 없이 전체 재실행하지 않는다.

### 4.4 예약·수동 작업과 대상 DB

| 작업 | 실행 방식 | 대상 DB | 시작 조건 | 완료 증거 |
|---|---|---|---|---|
| 최근 실거래 자동 동기화 | 예약 workflow | 운영 | 동일 stage 미실행, 호출량 여유 | 월별 결과·실패 queue·heartbeat |
| 농어촌민박·한옥 자동 동기화 | 독립 예약 workflow | 운영 | source별 배정량·상태 키 확인 | source별 신규·변경·오류 |
| 정기 API 통합 동기화 | 예약 workflow | 운영 | 독립 stage 제외 확인 | stage별 done/deferred/failed |
| 실패 단계 재시도 | 관리자 수동 | 운영 | 원인 해소, 완료 stage 보존 | 새 run ID와 실패 stage 감소 |
| 정부 숙박 CSV 적재 | 운영자 수동 | 개발 | 실제 DB 지문 확인 | batch·SHA·행 수·review |
| 숙박 manifest 승격 | 예약 또는 승인 수동 | 운영 | 최신 승인·dry-run·잠금 | 감사 표식·비교·통계 갱신 |
| 개발→운영 일반 병합 | workflow 수동 | 양 DB | dry-run 별도 승인 | 추가·수정·충돌·통계 marker |

일반 Shell에서 `--source manual`을 단독 실행하지 않는다. 관리자 기능이 만든 run ID 소유권 없이 시작한 수동 명령은 표준 절차가 아니다.

### 4.5 서비스키 버킷과 직렬화

국토부 실거래, 건축HUB, 행안부 숙박, 고캠핑, 농어촌·한옥, 관광펜션과 상가정보는 공급자별 카운터를 사용한다. 확인된 일일 한도의 80%를 soft cap으로 두며, 같은 공급자·키를 공유하면 직렬화한다. 건축물대장과 인허가는 서로 다른 요일로 분리하고, 농어촌·한옥은 사전 분할된 독립 배정량만 병렬 사용한다. `dry-run`도 외부 API를 호출하면 실제 한도를 소모한다.

### 4.6 stage 상태·run ID·heartbeat

`running`은 최근 heartbeat와 실제 프로세스를 함께 확인한다. `done`은 정상 완료, `deferred`는 선행조건·한도로 보류, `failed`는 오류, `cancelled`는 안전 중단, `partial`은 일부 commit 가능성을 뜻한다. 상태만 보고 재실행하지 않고 마지막 처리 page·월·index, stop reason, retryable, 호출량과 업무 지표를 함께 본다.

### 4.7 장시간 작업과 DB 재접속

안전한 처리 단위마다 commit·체크포인트를 남긴다. DB 연결이 끊기면 재접속 후 기존 run ID 소유권을 다시 확인하고 마지막 미완료 단위만 멱등 재실행한다. 새 run이 소유권을 가진 뒤 과거 run이 상태를 덮어쓰지 못하게 한다.

### 4.8 레거시 직접 수집 전환기

기존 운영 직접 수집과 staging 승격이 병존하는 동안 같은 원본 writer를 DB 잠금으로 직렬화한다. 검증된 대체 경로 없이 기존 수집을 중단하지 않고, 원본별 현재 경로·대상 DB·승인 여부를 상태 기록에 명시한다. 상세 stage와 복구 명령은 배포 묶음의 RUN-SYNC-001을 따른다.

## 5. staging·검증·승격

### 5.1 검증 게이트

출처·기준일·SHA-256·행 수, 인코딩·헤더, 관리번호, 업태·상태, 주소, 객실·사이트 수, snapshot 중복과 기존 원장 diff를 확인한다. 미분류·충돌·복수후보는 `review_required`로 보존한다.

### 5.2 승인과 manifest

미해결 review가 0건인 변경분만 승인 payload로 고정한다. manifest는 원본 지문, 운영 기준선, 승인 payload와 검토 계보를 묶는다. 승인 후 원본 해시·행 수·계보가 달라지면 새 승인과 manifest가 필요하다.

### 5.3 dry-run과 실제 반영

dry-run에서 신규·수정·상태변경·동일·보류, 기존 연결 보존, 신규·충돌·복수후보, 공란 덮어쓰기와 원본 지문을 확인한다. 실제 반영은 잠금과 run ID 소유권을 확보하고 감사 표식·통계 무효화를 같은 흐름에서 기록한다.

## 6. 원본별 운영 기준

### 6.1 주요 원본

- 건축물대장·인허가: 공유 건축HUB 한도를 직렬화하고 실제 응답 건수와 index를 함께 확인한다.
- 실거래: 실패한 월만 rollback·재적재하고 API 성공 월은 재호출하지 않는다.
- 일반·생활숙박: 서버 업태 필터가 없으므로 전 페이지를 실제 응답 길이 기준으로 순회한다.
- 농어촌민박·한옥·관광펜션: source별 상태와 배정량을 분리한다.
- 캠핑: 정부 CSV는 법정 허가·상태, 고캠핑은 설명·운영·사이트 세부정보를 보강한다.

### 6.2 캠핑 시설수

```text
캠핑 시설수
= 정상영업 건물 연결 고유시설
  + 정상영업 미연결 대지형 고유시설
  - 주소+정규화 상호 등 신뢰 가능한 동일 시설 중복
```

건물 연결 행은 건물당 하나로 묶고, 신뢰 키가 없는 미연결 행은 과도하게 합치지 않는다. 고캠핑 응답 건수는 전국 시설수의 단독 기준이 아니다.

### 6.3 캠핑 사이트 4분류

| 분류 | 정의 |
|---|---|
| 일반야영 | 일반야영 사이트 수 |
| 자동차야영 | 자동차야영 사이트 수 |
| 글램핑 | 글램핑 사이트 수 |
| 카라반 | 설치 카라반 + 개인 카라반 사이트 |

`사이트 합계 = 일반야영 + 자동차야영 + 글램핑 + 카라반`이다. 둘 이상 양수면 내부 `confirmed_mixed`, 값이 없거나 모두 0이면 `unknown`이며 내부에서는 둘을 분리한다.

### 6.4 건축물대장·건축인허가

건축물대장은 법정동·조회 index부터 재개하고 빈 HTTP 성공을 완료로 보지 않는다. 표제부·총괄표제부·인허가가 같은 공급자 한도를 공유하는지 확인한다. 신규 건물, 좌표·표제부 보강, 실패 법정동과 마지막 성공 index를 완료 증거로 남긴다.

### 6.5 실거래

최근 자동 수집과 장기 backfill이 같은 버킷을 동시에 소진하지 않게 한다. 월 적재 중 DB 오류는 해당 월을 rollback하고, 실패 queue의 월만 재호출한다. 최신 거래월, 월별 중복과 실패 queue 감소를 확인한다.

### 6.6 일반·생활·관광·농어촌·한옥

행안부 숙박은 업태 필터가 없고 응답이 요청 행 수와 무관하게 100행일 수 있으므로 실제 응답 길이로 종료한다. 농어촌·한옥·관광펜션은 source별 상태·체크포인트·배정량을 분리한다. 누락 필드를 기존 값 삭제로 해석하지 않는다.

### 6.7 상가·중개업소와 사진

상가·중개업소 수집은 건물 공적 식별키와 공급자별 batch·실시간 배정량을 구분한다. 사진은 제9장의 공급자 우선순위와 제8장의 공개 파생본·인증값 금지 규칙을 동시에 충족해야 한다.

## 7. 통계 산식과 공개 정책

### 7.1 유형별 산식표

| 유형 | 분자 | 분모 | 단위 |
|---|---|---|---|
| 생활 | 건물별 호실수 상한 적용 활성 신고객실 | 생활숙박 호실수 | 객실 |
| 일반 | 활성 고유 신고업체 | 일반숙박 건물 | 업체/건물 |
| 관광·에어비앤비·농어촌·한옥·복합 | 활성 신고 연결 건물 | 해당 유형 건물 | 건물 |
| 캠핑 | 활성 신고 연결 건물 | 캠핑 건물 | 건물, 시설·사이트는 별도 |

분모 0은 `null`·화면 `-`로 표시하고 소수점 첫째 자리로 반올림한다. 같은 신고가 여러 유형 원본에 나타나면 관리번호 등 승인 식별자로 중복 제거한다.

### 7.2 캠핑 통계

시설수는 6.2, 사이트수는 6.3을 단일 기준으로 사용한다. 사이트 수 확보율은 데이터 품질지표이며 신고율이 아니다. 공개 화면은 캠핑에서 건물수보다 시설수, 호실수보다 사이트수를 우선한다.

### 7.3 공개·내부 분리

공개에는 최종 건물·시설·업체·객실·사이트 합계와 최종 신고율만 제공한다. 비활성 상태별 수, 내부 분자·분모, 관리번호·원본·검토 메모·매칭 신뢰도는 관리자 전용이다.

## 8. 공개 데이터·개인정보 보호

### 8.1 최소 공개

공개, 로그인, 소유자, 배정 중개사, 관리자의 projection을 분리한다. 관리자 객체를 공개 route에서 필터 없이 재사용하지 않는다. 권한·소유권·공개범위를 확인할 수 없으면 응답하지 않는다.

### 8.2 금지 항목

- 휴업·폐업·취소·말소 상태와 날짜, 상태별 통계
- 연락처, 인증번호, 비밀번호·세션·재설정 토큰, 원본 IP
- 제한공개 매물의 정확 위치·자동 건물값·사진
- 내부 ID·run ID·상태 키·검토 메모·원본 오류
- API 키·DB URL·서명 URL·저장소 내부 객체 키

### 8.3 사진·파일

공개 사진은 권리·공개범위와 파일 형식을 확인하고 EXIF·GPS·원본 파일명·저장 키를 제거한 파생본을 사용한다. 파일 다운로드도 매 요청마다 권한을 확인하며 사용자별 응답은 공유 캐시하지 않는다.

## 9. 캐시·지도·사진 갱신

### 9.1 캐시와 통계

운영 쓰기는 통계 invalidation marker를 기록하고 worker가 polling 후 rebuild한다. 대량 반영 뒤 갱신시각과 여러 worker 응답을 확인한다. cold start·warming이 장시간 지속되면 관리자 refresh 후 원인을 확인한다.

### 9.2 사진 공급자

승인 자체사진 → TourAPI → Google Street View → 기존 호환 공급자 순서다. TourAPI metadata를 먼저 확인하고 최근 no-match/no-photo일 때만 Street View를 보조 사용한다. 공급자 키가 포함된 URL을 저장·반환하지 않는다.

### 9.3 갱신 검증

지도 신규 건물, 건물 상세, 전국·지역 통계, 사진 대표 우선순위를 같은 반영 시점의 표본으로 확인한다. 예열은 지연을 줄이는 유지보수이며 원본 승인이나 운영 승격을 대체하지 않는다.

## 10. 관리자 운영과 장애 대응

### 10.1 상태별 처리표

| 증상 | 중단 기준 | 복구 | 완료 증거 |
|---|---|---|---|
| stage 장시간 running | heartbeat 5분 초과 + 프로세스 없음 | stale 회수 후 실패 stage만 재시도 | 새 run ID, 체크포인트 연속 |
| HTTP 401/403 | 인증 실패 지속 | Secret 권한 복구 후 해당 stage 재시도 | 로그 비밀값 없음 |
| HTTP 429 | soft/hard cap 또는 반복 429 | 다음 KST 날짜에 체크포인트 재개 | 카운터 날짜·호출 연속 |
| DB 연결·잠금 | 소유권 불명 또는 사용자 지연 | commit·blocker 확인 후 멱등 재실행 | 중복·부분행 없음 |
| 원본 지문 변경 | 승인 후 해시·행 수 변화 | 새 staging·승인·manifest | 새 dry-run |
| 공개 금지정보 발견 | 즉시 | route·캐시 차단 후 역할별 회귀검사 | API·HTML·파일 재검사 |

### 10.2 운영 체크리스트

- [ ] 대상 DB, stage, run ID와 실제 프로세스를 확인했다.
- [ ] 공급자 호출량·공유 writer·중복 실행을 확인했다.
- [ ] 마지막 commit과 체크포인트를 기록했다.
- [ ] 완료 stage는 보존하고 실패 단위만 재시도했다.
- [ ] 반영 뒤 통계·지도·상세·사진과 공개 금지필드를 확인했다.

### 10.3 관리자 버튼·route·workflow·DB 대응표

| 운영 기능 | 시작 위치 | 대상 DB | 누르면 안 되는 경우 | 확인 지점 |
|---|---|---|---|---|
| 전체 정기 동기화 | 관리자 데이터 동기화 | 운영 | 예약 통합 실행 중 | 전체·stage 상태와 heartbeat |
| 실패 단계 재시도 | 관리자 데이터 동기화 | 운영 | 원인 미해소, 완료 stage 재실행 우려 | failed/deferred/cancelled만 재개 |
| 실거래 동기화 | 관리자 또는 지정 workflow | 운영 | 같은 월 수집·backfill 실행 중 | 실패 월 queue와 최신 거래월 |
| 건축HUB 수집 | 지정 workflow | 운영 | 인허가와 공유 한도 충돌 | 진행 index·실패 법정동 |
| 숙박 CSV inspect/staging | 승인 관리자 절차 | 개발 | DB 지문 불명, 8종 불완전 | source batch·review |
| 숙박 운영 승격 | `lodging_promotion` 또는 승인 CLI | 운영 | 미해결 review·원본 지문 변화 | manifest·dry-run·감사 표식 |
| 통계 즉시 갱신 | `POST /api/admin/stats/refresh` | 운영 캐시 | 원본 반영 미완료 | 갱신시각·worker 응답 |
| 사진 metadata 사전조회 | `POST /api/admin/prewarm-tourapi-metadata` | 운영 | 동일 작업 실행·공급자 장애 | 사진 상태 API·페이지·매칭 |
| 개발→운영 병합 | dry-run/실제반영 workflow | 양 DB | dry-run 미승인 | 추가·수정·충돌·marker |

실제 화면 문구가 달라져도 기능명, route·workflow와 대상 DB를 기준으로 판단한다. 실행 직전 현재 `--help`, 관리자 상태와 workflow 설정을 다시 확인한다.

### 10.4 장애 기록과 승인

장애 기록에는 대상 환경, run ID, 마지막 heartbeat·commit·checkpoint, 원인 분류, 중단·복구 조치, 전후 지표와 공개 표본 판정을 넣는다. 인증값·개인정보·공급자 원문 응답은 복사하지 않는다. 대량 증감, 기준선 변화, 공개 사고는 승인자 판정 없이 정상 완료로 닫지 않는다.
