# 홈앤스테이 데이터 수집·검증·승격·노출·갱신 통합 정책 및 운영 매뉴얼

**문서 버전:** V.03.0  
**기준일:** 2026-09-04  
**문서 상태:** 현행 운영 기준  
**적용 범위:** 숙박업 신고, 건축물대장, 건물마스터, 실거래, 농어촌민박, 한옥체험업, 캠핑·야영, 관광숙박, 상가업소, 건물사진, 공개 통계  
**이전 문서와의 관계:** V.01 및 V.02 계획·단계 보고서의 원칙을 계승하되, 현재 구현과 실제 운영 절차는 본 문서를 우선한다.

---

## 1. 문서 목적

이 문서는 데이터가 외부 원본에서 수집되어 개발 DB에서 검증되고, 승인된 결과가 운영 DB에 반영되며, 지도·목록·상세·통계·사진으로 노출되는 전 과정을 하나의 운영 정책으로 정의한다.

운영자는 이 문서만으로 다음 질문에 답할 수 있어야 한다.

1. 어떤 작업이 자동으로 실행되는가?
2. 어떤 작업은 개발 관리자에서 승인해야 하는가?
3. 어떤 작업은 운영 관리자 또는 Replit 워크플로에서 수동 실행해야 하는가?
4. 배포 버튼을 누르면 코드와 데이터 중 무엇이 이동하는가?
5. 데이터가 바뀐 뒤 지도와 통계는 언제 갱신되는가?
6. 실패하거나 중단되면 어디서 재시작하고 무엇을 확인해야 하는가?
7. 휴업·폐업 등 보호가 필요한 정보는 공개 화면에서 어떻게 차단되는가?

## 2. 최상위 운영 원칙

### 2.1 운영 DB 직접 반영 최소화

- 신규 대량 원본은 원칙적으로 개발 DB의 staging에 먼저 적재한다.
- 파싱·분류·중복·상태·주소 매칭 검증을 통과한 승인 데이터만 운영 후보가 된다.
- 운영 반영 전에는 항상 dry-run으로 추가·수정·상태변경·보류 건수를 확인한다.
- 운영 반영은 명시적 관리자 승인 또는 명시적 실제반영 워크플로를 통해서만 수행한다.
- 정부 숙박 CSV 정기 승격은 staging 변경분의 관리자 승인이 그 운영 반영
  전제까지 포함한다. 승인된 최신 8종이 readiness gate를 통과하면 예약된
  `lodging_promotion` stage가 manifest 생성·자동승인·dry-run·운영 반영·병행
  비교를 한 실행에서 수행할 수 있다.

### 2.2 코드 배포와 데이터 승격 분리

- **Publish/Deploy는 코드와 정적 파일을 배포한다.**
- **개발 DB 데이터는 Publish만으로 운영 DB에 복사되지 않는다.**
- 데이터 승격은 승인 manifest 또는 개발→운영 병합 절차를 별도로 실행해야 한다.
- 개발과 운영의 `master_buildings.id`는 같은 숫자라도 같은 건물을 의미하지 않을 수 있다.
- 환경 간 동일 건물 비교는 관리번호, 공적 식별키 또는 정규화 주소로 한다.

### 2.3 실패 시 닫힘

- 개발 DB인지 확인할 수 없으면 staging 적재를 중단한다.
- 승인 원본의 해시·행 수·계보가 달라지면 운영 승격을 중단한다.
- 필수 원본, 최신 승인, 미해결 검토행 또는 운영 기준선을 확인하지 못하면 반영하지 않는다.
- 실패를 성공처럼 표시하거나 임의의 기본값으로 통과시키지 않는다.

### 2.4 멱등성과 재실행

- 같은 원본·기준일·해시의 staging 배치는 중복 생성하지 않는다.
- 운영 승격은 같은 승인 payload를 재실행해도 중복 행을 만들지 않아야 한다.
- 장시간 작업은 진행상태, 마지막 처리 위치, run ID 또는 상태 키를 남긴다.
- 중단 후에는 처음부터 무조건 다시 시작하지 않고 저장된 체크포인트에서 이어간다.

### 2.5 공개 최소화

- 공개 API에는 서비스 제공에 필요한 최소 필드만 제공한다.
- 휴업·폐업·취소·말소 상태와 상태별 건수는 일반 사용자에게 공개하지 않는다.
- 동일 건물에 정상 신고와 과거 비활성 신고가 함께 있으면 정상 신고를 우선한다.
- 정상 신고 없이 비활성 이력만 있는 건물은 신고율 계산의 분모로만 사용할 수 있다.
- 제한공개 매물은 자동 건물값을 포함해 비공개 필드가 우회 노출되지 않게 한다.

## 3. 환경과 책임 경계

| 구분 | 개발 환경 | 운영 환경 |
|---|---|---|
| 주 DB | `DATABASE_URL` | `PROD_DATABASE_URL`을 런타임 `DATABASE_URL`로 사용 |
| 목적 | 수집 시험, staging, 검증, 승인, 기능 테스트 | 실제 사용자 서비스, 예약 동기화, 승인 데이터 반영 |
| 자동 예약 수집 | 원칙적으로 없음 | 정기 API 통합·실거래·농어촌민박·한옥 예약 실행 |
| 정부 CSV 8종 | staging 및 승인 원본 | 승인 manifest를 통해서만 반영 |
| 코드 변경 확인 | 개발 workflow 재시작 후 확인 | Publish 후 운영 확인 |
| 데이터 이동 | 운영으로 자동 이동하지 않음 | 수동 승격 또는 병합으로 받음 |

### 3.1 DB 식별 안전 규칙

- URL 문자열이나 환경 이름만 보고 개발·운영 DB를 판단하지 않는다.
- 실제 DB 지문을 독립 연결로 비교한다.
- 개발 staging 연결이 운영 DB와 같거나 확인할 수 없으면 적재를 차단한다.
- 운영 작업 전에 대상 DB를 로그와 관리자 상태 화면에서 다시 확인한다.
- 운영 DB 접속값이나 API 키는 문서·로그·채팅에 출력하지 않는다.

## 4. 데이터 생명주기

```text
외부 원본/API
  → 원본 식별·해시·기준일 기록
  → 개발 staging 적재
  → 형식·필수값·분류·상태·중복 검증
  → 주소 및 기존 운영 데이터 비교
  → 자동통과 / 검토필요 분리
  → 승인 payload 고정
  → 운영 기준선 manifest 생성
  → 운영 dry-run
  → 정기 자동승격: 즉시 운영 반영·병행 비교
    또는 수동승격: dry-run 최종 승인 후 운영 반영
  → 통계 캐시 무효화
  → 지도·목록·상세·통계 확인
  → 일정 기간 관찰
```

기존 운영 API 수집기는 전환 기간 동안 일부 원본을 운영 DB에 직접 갱신한다. 이 경로도 상태 키, 잠금, 할당량, 재시도와 통계 무효화 규칙을 따라야 한다.

### 5.2 서비스 분류 원칙

- 관광: 관광숙박업, 관광호텔, 휴양콘도미니엄업, 관광펜션업
- 일반: 일반호텔, 여관업, 여인숙업, 숙박업 기타
- 생활: 숙박업 생활
- 에어비앤비: 외국인관광 도시민박
- 농어촌민박, 한옥, 캠핑은 별도 유형 유지
- 서로 다른 별도법 허가가 한 건물에 함께 있으면 복합
- 건축물대장 용도와 영업신고 업태는 별도 필드로 보존
- 원문 업태를 서비스 분류로 덮어쓰지 않는다.

### 5.3 상태 우선순위

1. 같은 건물에 정상과 비활성 신고가 모두 있으면 정상 우선
2. 정상 신고만 있으면 공개 목록·활성 통계에 사용
3. 비활성 신고만 있으면 원장에는 보존하되 공개하지 않음
4. 비활성-only 건물은 정책상 필요한 신고율 분모에만 사용
5. 알 수 없는 상태는 자동 활성 처리하지 않고 검토 대상으로 둠

## 6. 자동 실행 정책

### 6.1 현재 예약 워크플로

| 워크플로 | 실행 시각 | 대상 | 자동 수행 | 운영자 개입 |
|---|---|---|---|---|
| 최근 실거래 자동 동기화 | 매일 02:00 | 운영 DB | 실거래 stage | 실패 상태일 때 재시도 |
| 농어촌민박 자동 동기화 | 매일 02:00 | 운영 DB | 농어촌민박 stage | 실패·할당량 초과 확인 |
| 한옥체험업 자동 동기화 | 매일 02:00 | 운영 DB | 한옥 stage | 실패·할당량 초과 확인 |
| 정기 API 통합 동기화 | 매일 02:30 | 운영 DB | 위 세 stage를 제외한 통합 stage | 상태 요약 및 실패 stage 재시도 |
| Weekly Digest | 매주 금요일 01:00 | 운영 서비스 | 주간 이메일 | 발송 실패 확인 |
| Deal Alert Digest | 매일 00:00 | 운영 서비스 | 급매 알림 | 발송 실패 확인 |

예약 워크플로는 Replit workspace가 아닌 배포 환경에서 동작해야 한다. workspace는 절전될 수 있으므로 shell 백그라운드 작업을 정기 운영 수단으로 사용하지 않는다.

### 6.2 단계별 주기

`scheduled_sync.py`는 stage별 주기와 API 할당량을 적용한다.

- 실거래: 매일
- 건축물대장 표제부/총괄 관련 stage: 설정된 요일·할당량
- 준공 전 건축인허가: 설정된 요일
- 숙박 관련 API: 각 원본 주기와 서비스키 버킷에 따라 실행
- 농어촌민박·한옥: 독립 상태 키로 실행

동일 서비스키나 일일 한도를 공유하는 단계는 직렬화한다. 확인되지 않은 API 한도를 추정해 늘리지 않으며 확인된 한도의 80% 이내를 정기 배정 기준으로 삼는다.

### 6.3 자동 갱신 범위

- 동기화 성공 시 DB 변경분을 커밋한다.
- 관련 쓰기 경로는 통계 무효화 marker를 기록한다.
- 앱 worker는 약 10초 간격으로 marker를 확인하고 백그라운드 통계를 재생성한다.
- 이는 WebSocket식 즉시 push가 아니라 짧은 polling 지연이 있는 준실시간 방식이다.
- 건물 상세의 일부 외부 정보는 첫 요청 후 백그라운드로 수집되어 다음 요청부터 보일 수 있다.

## 7. 수동 실행 작업과 버튼

화면 문구는 배포 버전에 따라 달라질 수 있다. 운영 판단의 기준은 기능명과 연결된 route/workflow다.

| 기능/버튼 | 실행 위치 | 대상 DB | 사용 시점 | 실행 후 확인 |
|---|---|---|---|---|
| 전체 정기 동기화 실행 | 관리자 데이터 동기화 | 현재 서버가 연결한 DB, 운영에서 실행 권장 | 예약 시간을 기다리지 않고 전체 수집할 때 | scheduled sync 상태·stage별 결과 |
| 실패 단계 재시도 | 관리자 데이터 동기화 | 운영 DB | failed/deferred/cancelled stage가 있을 때 | 완료 stage가 재실행되지 않는지 |
| 실거래 동기화 | 관리자 또는 workflow | 운영 DB | 최신 거래 즉시 반영 | 삽입 수, 실패 월, 상태 heartbeat |
| 건물수집 실행 | 관리자 `sync-brhub` | 운영 DB | 표제부 전수·증분 수집 | `brhub_sync_status`, 체크포인트 |
| 건축정보 채우기 | 관리자 title-info | 운영 DB | 표제부 세부값 보강 | 완료·실패 수, 재실행 가능 여부 |
| 준공 전 인허가 수집 | 예약 stage 또는 별도 실행 | 운영 DB | 허가·착공 신규분 반영 | permit 상태 및 할당량 |
| 숙박업 동기화 | 관리자 legacy lodging sync | 운영 DB | 전환기 API 직접 수집이 필요할 때 | 신규·변경·오류 건수 |
| 상가정보 수집 | 관리자 stores sync | 운영 DB | 입점 상가 캐시 보강 | 일일 batch 카운터·진행 ID |
| 부동산업소 수집 | 관리자 realty sync | 운영 DB | 입점부동산 목록 보강 | 저장 건물·실패 건물 |
| 건물사진 동기화 | 관리자 photos sync | 운영 DB | 사진 원본/메타 갱신 | provider별 성공·no-match |
| 통계 즉시 갱신 | 관리자 stats refresh | 운영 DB 캐시 | 반영 후 수치가 즉시 필요할 때 | 약 10초 후 공개·관리자 통계 비교 |
| 개발→운영 dry-run | Replit workflow | 양 DB 읽기 | 일반 건물·거래 병합 전 | 추가·수정·충돌 수 |
| 개발→운영 실제반영 | Replit workflow | 운영 DB 쓰기 | dry-run 승인 후 | 운영 건수·표본·통계 marker |

### 7.1 누르면 안 되는 경우

- 다른 동일 stage가 실행 중인 경우
- 일일 API 한도가 거의 소진된 경우
- DB 대상이 개발인지 운영인지 확인되지 않은 경우
- staging 최신 원본이 검증되지 않은 경우
- 미해결 review 행이 남은 경우
- dry-run 결과가 예상 기준선을 벗어난 경우
- 장시간 수집기와 운영 승격 잠금이 충돌하는 경우

---

## 8. 정부 CSV 8종 개발 staging 운영 매뉴얼

### 8.1 1단계 — 원본 준비

- 정부 원본 파일명과 원본 종류를 확인한다.
- 기준일, 다운로드 출처, 파일 해시를 기록한다.
- CSV 인코딩과 헤더를 확인한다.
- 캠핑 XLSX 등 별도 importer가 필요한 형식은 8종 공통 CSV staging과 혼동하지 않는다.

### 8.2 2단계 — 개발 staging 적재

- 반드시 개발 DB에서 실행한다.
- 시스템의 실제 DB 지문 검사를 통과해야 한다.
- 같은 원본·기준일·해시는 기존 배치를 재사용한다.
- 원문 JSON과 정규화 결과를 모두 보존한다.

### 8.3 3단계 — 자동 검증

자동 검증 항목:

- 필수 관리번호
- 원본 종류와 업태 허용값
- 영업상태 허용값
- 주소 존재 여부와 정규화 결과
- 객실수·사이트수 형식
- 동일 snapshot 중복
- 기존 원장 대비 new/changed/status_change/unchanged
- 원본 간 중복과 관리번호 충돌

검증 결과는 자동통과와 검토필요로 분리한다.

### 8.4 4단계 — 관리자 검토

개발 관리자에서 다음을 확인한다.

- 원문과 정규화 값
- 기존 운영 값과 변경값
- 주소 매칭 후보와 신뢰도
- 업태·서비스 분류
- 상태 변경
- 객실수/사이트수 이상치
- 자동통과할 수 없는 중복·충돌

검토 결정은 최신 자식 manifest로만 이어지는 선형 계보를 유지한다. 부분 해결 시 해결되지 않은 행을 새 manifest에서 누락시키지 않는다.

### 8.5 5단계 — 승인 payload 생성

- 검증 완료 배치에서 변경분만 고정한다.
- 승인자 관리자 ID를 기록한다.
- 승인 이후 원본 행이나 해시가 바뀌면 기존 승인을 재사용하지 않는다.
- 승인 버튼은 운영 DB를 즉시 변경하지 않는다.

### 8.6 6단계 — 운영 기준선 manifest

대표 CLI:

```bash
python build_lodging_production_manifest.py --created-by <관리자ID> --output <manifest파일>
```

manifest에는 운영 기준선, 최신 source batch, 승인 payload, 검토 계보와 원본 지문이 포함되어야 한다.

### 8.7 7단계 — dry-run

관리자 dry-run 또는 CLI:

```bash
python apply_lodging_promotion.py <MANIFEST_ID>
```

반드시 확인할 값:

- 원본 8종 모두 존재
- 최신성 기준 충족
- 미해결 review 0건
- 신규·변경·상태변경·동일·보류 건수
- 운영 기존 연결 보존 여부
- 주소 매칭률과 충돌률
- 운영 원본 지문이 manifest 생성 이후 바뀌지 않았는지

### 8.8 8단계 — 최종 승인 및 운영 반영

수동 승격은 dry-run 결과가 승인된 뒤에만 운영 반영 버튼을 누른다.

정기 자동승격에서는 관리자에게 staging 변경분을 승인하는 시점이 운영 반영
전제에 대한 승인이다. 최신 8종·최신성·미해결 review 0건·변경분 승인 조건을 모두
충족하면 `lodging_promotion` stage가 manifest 생성, 자동승인, dry-run, 운영
반영과 병행 비교를 연속 수행한다. 한 조건이라도 충족하지 않거나 병행 비교가
차단되면 성공으로 처리하지 않는다.

- 실제 수집기와 승격 작업은 DB 잠금으로 직렬화한다.
- staging 원본 지문을 다시 확인한다.
- 운영 쓰기 후 감사 표식을 커밋한다.
- 중간 실패 시 run ID 소유권과 커밋 여부를 확인한 뒤 멱등 재실행한다.
- 이미 커밋된 데이터의 감사 표식 복구는 원본 변경 여부와 분리해 처리한다.

### 8.9 9단계 — 반영 후 확인

- 운영 `lodging_registry` 건수와 상태별 내부 건수를 확인한다.
- 신규·변경 표본을 관리자에서 확인한다.
- 공개 목록에는 정상영업만 노출되는지 확인한다.
- 지도 분류, 건물 상세, 전국 통계가 같은 분류 규칙을 쓰는지 확인한다.
- 통계 marker 처리 후 수치가 갱신되는지 확인한다.

## 9. 일반 개발→운영 병합 매뉴얼

정부 CSV 승인 승격과 일반 건물·거래 병합은 서로 다른 절차다.

### 9.1 dry-run

Replit workflow:

```text
Merge Dev→Prod (dry-run)
```

동등 명령:

```bash
python -u merge_dev_to_prod.py --dry-run
```

확인 항목:

- 개발·운영 DB가 서로 다른지
- 신규 건물·거래 수
- 기존 건물 매칭 키
- 충돌·보류·삭제 가능성
- 개발 내부 ID가 운영 ID로 잘못 사용되지 않는지

### 9.2 실제 반영

dry-run 결과를 저장하고 승인한 뒤:

```text
Merge Dev→Prod (실제반영)
```

동등 명령:

```bash
python -u merge_dev_to_prod.py
```

실제반영 후 운영 통계 무효화 marker가 기록되는지 확인한다.

### 9.3 금지

- dry-run 없이 실제반영
- 운영 DB 백업·기준선 없이 대량 덮어쓰기
- 개발 `master_buildings.id`를 운영 ID로 직접 복사
- 한 번 실패한 반영을 커밋 상태 확인 없이 반복

## 10. 데이터 검증 게이트

### 10.1 형식 검증

- 인코딩과 헤더
- 관리번호와 주소
- 날짜·숫자·좌표
- 허용 업태와 상태
- 사이트 수와 객실 수의 의미 구분

### 10.2 중복 검증

- 같은 관리번호는 원장 단위에서 식별한다.
- 원본이 다른 동일 시설은 주소·허가일·객실수·정규화 상호명을 사용해 중복 검토한다.
- 서로 다른 관리번호는 같은 주소라도 원장에 보존할 수 있다.
- 통계는 지표 목적에 따라 신고번호 또는 대표 건물 기준으로 중복 제거한다.

### 10.3 주소 매칭

- 도로명 우선, 지번 보조
- 괄호 지역명은 읍·면처럼 필요한 경우만 복원
- 지역 통합·행정구역 변경은 명시적 정규화 규칙 사용
- 운영 기존 연결을 개발 매칭보다 우선 기준선으로 비교
- 개발 매칭률을 운영 매칭률로 오해하지 않는다.

### 10.4 운영 승격 중단 기준

- 예상 대비 대량 감소 또는 급증
- 기존 정상 신고의 비활성 전환 급증
- 관리번호 충돌
- 주소 미매칭 급증
- 캠핑 사이트 수 또는 객실 수 파싱 이상
- 승인 원본 지문 변경
- 운영 DB 잠금·연결 불안정
- 공개 표본에서 개인정보 또는 비활성 상태 노출

## 11. 공개 노출 정책

### 11.1 공개 가능

- 서비스 분류
- 공개 가능한 건물·시설 기본 정보
- 정상영업 신고 기반의 업체·객실·사이트 집계
- 신고 이력이 연결된 건물 기준 신고율
- 공개 사진 provider 결과

### 11.2 공개 금지

- 개별 휴업·폐업·취소·말소 상태
- 공개 통계의 비활성 상태별 건수
- 내부 검토 메모와 매칭 신뢰도
- staging 원문·오류 상세
- 비공개 매물의 자동 건물값
- API 키가 포함된 공급자 URL

### 11.3 일반숙박 신고율

- 같은 건물에 정상과 비활성 신고가 있으면 정상으로 계산
- 정상 신고가 연결된 건물은 분자와 분모에 포함
- 비활성 신고만 연결된 건물은 분모에만 포함
- 어떠한 영업신고도 연결되지 않은 대장상 숙박시설은 신고율 분모에서 제외
- 공개 응답은 건물수, 정상 신고업체/객실수, 신고율만 제공
- 비활성 상태와 내부 분자·분모 필드는 공개 API에서 제거

### 11.4 캠핑

- 캠핑은 건물·호실이 아니라 시설·사이트 기준
- 정상영업 신고시설의 신고율은 100%
- 사이트 수 확보율은 데이터 품질지표이며 신고율이 아님
- TM 좌표는 검증된 좌표계로 변환한 뒤 시설 마커에 사용

### 11.5 사진

- 우선순위: 보유/승인 사진 → TourAPI metadata → Google Street View 보조
- TourAPI 공급자 키가 포함된 URL을 공개 저장하지 않는다.
- Street View는 TourAPI 미매칭 또는 사진 없음 조건과 품질검사를 통과한 경우만 사용한다.
- 고층은 주변 공식 파노라마 후보와 거리·pitch·fov를 계산한다.

## 12. 캐시와 실시간 갱신 정책

| 대상 | 갱신 방식 | 예상 지연 | 수동 조치 |
|---|---|---:|---|
| 전국 통계 | DB invalidation marker → worker polling → rebuild | 약 10초 이상 | 관리자 통계 즉시 갱신 |
| 지도 건물 | DB 좌표·분류 조회와 지도 캐시 | 경로별 상이 | 신규 건물 표본 확인 |
| 건물 상세 | DB + 요청 시 외부정보 백그라운드 보강 | 첫 요청 이후 | 재방문 또는 상태 확인 |
| TourAPI 사진 | catalog metadata 예열 또는 요청 | 예열 상태에 따라 다름 | metadata prewarm |
| Street View | 요청 시 조건·할당량·품질검사 | 요청 시 | provider 오류 확인 |
| 정적 JS/CSS | content-addressed build | 배포 시 | frontend build 및 실제 렌더 확인 |

### 12.1 통계 수동 갱신이 필요한 경우

- 대량 운영 반영 직후 즉시 수치를 확인할 때
- marker 기록 실패가 의심될 때
- 여러 worker의 통계가 서로 다를 때
- 캐시가 warming 상태에서 오래 머물 때

관리자 기능:

```text
POST /api/admin/stats/refresh
```

### 12.2 예열 작업

다음은 실행 자체가 자동 예약되지 않았거나 운영자가 필요 시 실행하는 유지보수 작업이다.

```bash
python prewarm_tourapi_metadata.py
python geocode_buildings.py
python prewarm_unit_areas.py
```

예열은 사용자 요청 경로의 지연을 줄이기 위한 작업이며, 원본 승인이나 운영 승격을 대체하지 않는다.

## 13. 배포 정책

### 13.1 배포 전

```bash
npm run build:frontend
python -m py_compile app.py
python tests/smoke_test.py
python tests/api_test.py
```

추가 확인:

- 공개 API에 관리자 필드가 없는지
- 동일 건물 정상 우선 규칙
- 지도·목록·상세·통계 분류 일치
- 신규 스키마가 있으면 `SCHEMA_VERSION` 증가
- 운영 secrets와 API 권한 존재

### 13.2 Publish 시 자동

- production build 단계에서 frontend 정적 자산 생성
- production start script가 운영 DB 연결을 런타임에 설정
- Gunicorn worker 시작
- worker별 통계 백그라운드 서비스 시작
- 스키마 버전이 다를 때 초기화 경로 실행

### 13.3 Publish로 자동 처리되지 않는 것

- 개발 DB 데이터를 운영 DB로 복사
- 정부 CSV 승인 payload 운영 반영
- 개발→운영 병합
- 운영 통계 수치의 업무적 승인
- 실제 브라우저 화면 정상 여부 판단
- 모든 외부 API 예열

### 13.4 배포 후 수동 점검

```bash
curl -fsS https://<운영도메인>/api/health
curl -fsS https://<운영도메인>/api/v1/d/3f7
SMOKE_BASE_URL=https://<운영도메인> python tests/smoke_test.py
```

브라우저 확인:

- 홈 화면이 실제로 렌더링되는가
- 지도와 목록이 표시되는가
- 검색과 건물 상세 이동이 되는가
- 전국 숙박통계가 warming 후 정상 수치를 보이는가
- 사진이 TourAPI 우선, Street View 보조로 표시되는가
- 개발자 콘솔과 network에 치명적 오류가 없는가

현재 smoke 검사는 HTTP 200과 파일 형식 중심이므로 빈 화면을 완전히 잡지 못한다. 실제 렌더 확인은 자동 보완이 완료될 때까지 수동 필수다.

## 14. 장애·중단 복구

### 14.1 예약 동기화 실패

1. 관리자 scheduled sync 상태에서 실패 stage 확인
2. quota, 외부 API 오류, DB 오류 구분
3. 완료 stage는 유지하고 실패/deferred/cancelled stage만 재시도
4. 반복 실패 시 다음 예약 실행 전에 원인 수정

### 14.2 장시간 수집 중단

- 상태가 running이어도 heartbeat가 오래되면 interrupted로 간주
- 마지막 commit/checkpoint 확인
- run ID 소유권 재확인
- 작은 재처리 단위로 멱등 재실행
- shell detached 프로세스 대신 Replit workflow 사용

### 14.3 API 일일 한도 소진

- 호출을 강행하지 않는다.
- 실시간과 배치 할당량을 분리해 확인한다.
- 다음 한국 날짜에 체크포인트에서 재개한다.
- dry-run도 외부 API를 호출하면 한도에 포함된다는 점을 고려한다.

### 14.4 운영 승격 실패

- 실제 commit 여부를 먼저 확인한다.
- 원본 지문이 바뀌었으면 새 승인/manifest를 만든다.
- 일부 commit이 확인되면 동일 manifest로 멱등 복구한다.
- 운영 기존 연결과 감사 표식을 확인한다.
- 사용자 노출 이상이면 코드 롤백과 데이터 승격 복구를 분리해 판단한다.

## 19. 현재 전환 상태와 남은 주의사항

### 구현되어 있는 것

- 정부 CSV 8종 데이터 계약과 staging
- 원본 해시·기준일·원문 보존
- 검증·review·승인 payload
- 운영 baseline manifest와 readiness gate
- dry-run과 승인 기반 운영 승격
- 원본 지문 fence와 legacy 동기화 잠금
- 통계 invalidation marker와 worker rebuild
- 공개/관리자 통계 projection 분리
- 일반숙박 정상 우선 및 비활성-only 분모 규칙
- TourAPI 우선·Street View 보조 사진

### 전환기 병존

- 신규 staging/승격 경로와 기존 운영 직접 importer가 함께 존재
- 모든 원본이 staging-only로 완전히 전환된 것은 아님
- 일부 예열과 backfill은 수동 workflow
- 모든 통계 stale 상황에 대한 관리자 경보가 완전 자동화된 것은 아님
- 신규 건물 지도 캐시의 즉시 반영은 별도 확인 필요
- 배포 후 실제 브라우저 blank-page 검사는 아직 수동 보완 필요

전환기에는 기존 경로를 한 번에 삭제하지 않는다. 대체 경로가 여러 차례 정상 동작하고 결과가 비교 검증된 뒤 비활성화한다.

## 부록 A. 운영자가 반드시 기억할 다섯 문장

1. **Publish는 개발 DB 데이터를 운영 DB로 복사하지 않는다.**
2. **정부 CSV는 개발 staging에서 검증·변경분 승인해야 하며, 정기 자동승격은 그 승인 뒤 dry-run·반영·비교까지 이어진다. 예외적 수동승격만 dry-run 승인과 실제반영을 나눈다.**
3. **기존 정기 API 수집은 운영 DB에서 자동 실행되지만 실패 단계 재시도와 결과 확인은 운영자 책임이다.**
4. **휴·폐업 정보는 공개하지 않으며, 정상 신고가 같은 건물에 있으면 정상만 사용한다.**
5. **데이터 반영 완료는 DB commit이 아니라 지도·상세·통계·사진의 운영 표본 확인까지 끝난 상태를 뜻한다.**
