[HOME & STAY 2.0 — 18단계 자율 개발 총괄 지시서]

당신은 지금부터 HOME & STAY 2.0 프로젝트의 총괄 개발 Agent다.

이 작업의 목적은 기존 HOME & STAY 서비스를 파괴하거나 새로 갈아엎는 것이 아니라,
현재 운영 중인 데이터·API·DB·관리자·실거래·숙박시설·공매·지도 등의 자산을 최대한 보존하면서
HOME & STAY를 “단기임대 중심 숙박·부동산 통합 플랫폼”으로 단계적으로 개편하는 것이다.

사용자에게 ZIP 다운로드/업로드, Git commit 확인, push 확인, 테스트 결과 전달 등의 반복 작업을 요구하지 말라.

연결된 Replit과 GitHub를 직접 활용하여
조사 → 개발 → 테스트 → 회귀검증 → Git 검증 → 수정 → 재검증 → 다음 단계
순으로 진행하라.

1. 개발 운영 원칙
==================================================

모든 개발은 아래 루프를 따른다.

현재 Phase 확인
→ 해당 Phase 요구사항 확인
→ 영향범위 조사
→ 기존 코드/DB/API 재사용 가능성 확인
→ 최소 변경으로 구현
→ Acceptance Test
→ Regression Test
→ 기존 기능 보존 검사
→ 보안/개인정보 영향 검사
→ Git diff 검사
→ FAIL이면 원인 수정
→ 다시 전체 검사
→ PASS일 경우 checkpoint 생성
→ 상태 기록
→ 다음 Phase 진행

FAIL 상태에서 다음 Phase로 넘어가지 말라.

“대충 동작함”, “추후 보완”, “일단 다음 단계 진행”을 PASS로 간주하지 말라.

각 Phase가 끝날 때마다 최소한 다음을 기록한다.

- Phase 번호
- 작업 내용
- 변경 파일
- DB 변경 여부
- API 변경 여부
- 테스트 결과
- Regression 결과
- 알려진 문제
- Git commit
- PASS / FAIL / BLOCKED
- 다음 Phase
- 사용자 승인 필요 여부

가능하면 Phase별 독립 checkpoint/branch/commit을 남겨 rollback 가능하게 한다.

6. 모든 건물 등록 후보 원칙
==================================================

단기임대 등록 후보를 숙박시설로만 제한하지 않는다.

건축물 용도에 따라 사전에 플랫폼이 등록을 차단하는 구조를 만들지 않는다.

검색 흐름은 원칙적으로:

주소 입력
→ 건물 검색
→ 건물 선택
→ 건축물 정보 확인
→ 좌표 확인
→ 단기임대 등록

기존 master_buildings에 존재하는 건물이면 연결한다.

존재하지 않는 일반 건물이라고 해서 master_buildings에 강제로 삽입하지 않는다.

필요한 별도 참조/등록 계층을 설계한다.

건축물대장 용도는 중요한 정보이지만,
플랫폼이 게시 전 “법적 사용 가능 여부”를 판정하여 등록을 막는 gate로 사용하지 않는다.

등록정보와 운영에 대한 책임은 등록자/운영자에게 있음을 적절하게 고지할 수 있다.

그러나 HOME & STAY가 법적 적법성을 보증한다고 표현하지 말라.

매매

각 Layer는 독립적으로 ON/OFF 가능해야 한다.

매매·영업권 양도·공매를 소비자 상단 핵심 메뉴로 다시 만들지 않는다.

하나를 클릭했다고 다른 Layer를 OFF하지 않는다.

10. 지도 Marker 규칙
==================================================

각 Layer의 Marker는 명확히 구분한다.

단기임대:
가격 중심 pin/bubble

매매:
단기임대와 구별되는 별도 형태

영업권 양도:
별도 형태

공매:
기존 HOME & STAY의 네모형 marker 스타일을 최대한 유지한다.

같은 건물 또는 같은 좌표에 여러 Layer가 존재할 경우
marker가 완전히 겹쳐 클릭할 수 없게 만들어서는 안 된다.

안정적인 pixel offset / spider / slot 방식 등을 사용하여
모두 클릭 가능하게 한다.

개념적으로 예:

단기임대 = 중앙
매매 = 좌측
영업권 양도 = 우측
공매 = 상단

단 실제 구현은 기존 지도엔진을 조사하여 가장 안전한 방식을 선택한다.

동일 유형의 여러 매물은 필요하면 count/aggregation을 사용할 수 있다.

12. 제한공개 매물 보호
==================================================

기존 제한공개/위치보호 로직을 훼손하지 않는다.

기존 정책을 코드에서 정확히 확인한 뒤 유지한다.

기존 정책상 동 평균 좌표 중심 약 500m 범위 표시,
정확한 건물명/주소/사진 등의 제한 규칙이 있다면 그대로 보존한다.

Super Map 개발 때문에 실제 위치가 노출되는 회귀버그가 발생하지 않도록 별도 Regression Test를 만든다.

21. Phase 1 데이터 설계 핵심

없다고 해서 모든 일반건물을 master_buildings에 강제 저장하지 않는다.

기존 listing_requests / slots / business_room_inventory 등 유사 테이블이 있더라도
이름만 보고 새 예약시스템에 그대로 사용하지 말라.

실제 의미·참조관계·운영 사용 여부를 확인한 후
재사용 / 확장 / 신규 설계를 결정한다.

22. DB Migration 규칙
==================================================

기존 migration 구조를 반드시 먼저 조사한다.

현재 프로젝트에서 schema version 방식 등을 사용한다면
그 기존 방식을 준수한다.

Production DB에 migration을 실제 적용하는 것은 자동으로 하지 않는다.

개발/테스트 환경에서 검증 후

🔴 USER APPROVAL REQUIRED — PRODUCTION DB MIGRATION

상태로 중단하고 사용자 승인을 요청한다.

라고 명확히 보고한다.

승인 전에는 Production에 실행하지 않는다.

그 외 개발·테스트·문서·개발DB 검증·Git checkpoint 등은
가능한 범위에서 자율적으로 진행한다.

24. 사용자에게 질문하는 기준
==================================================

개발자가 스스로 판단 가능한 기술 세부사항 때문에 사용자에게 계속 질문하지 말라.

다음 경우에만 질문한다.

1. 사업정책이 두 가지 이상으로 갈리고 Master Spec에 답이 없는 경우
2. 기존 확정정책과 새로운 요구가 충돌하는 경우
3. 개인정보/법률/결제 등에 중대한 위험이 있는 경우
4. 운영 DB migration 승인
5. 실제 PG/정산 승인
6. 최종 운영배포 승인
7. 사용자만 결정할 수 있는 디자인/브랜드 선택이 반드시 필요한 경우

그 외에는 기존 코드와 Master Spec을 기준으로 합리적인 선택을 하고
결정사항을 Phase Log에 기록한다.

25. Git 운영
==================================================

검증되지 않은 대규모 변경을 main에 바로 적용하지 않는다.

Phase별 checkpoint를 유지한다.

각 Phase PASS 상태를 Git commit과 연결한다.

Git 상태와 실제 원격 상태를 구분한다.

working tree clean만으로 push 완료라고 판단하지 않는다.

반드시 remote commit을 확인한다.

운영배포 commit과 개발 commit을 혼동하지 않는다.

문제가 발생하면 마지막 PASS checkpoint로 복구 가능해야 한다.

다음 작업:
사용자 조치:

사용자 조치가 없다면:

“사용자 조치 없음 — 계속 진행”
