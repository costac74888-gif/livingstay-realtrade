name: 관리자 입점부동산 기준
description: 브로커 표준데이터와 상권정보 캐시가 함께 존재할 때 관리자 화면·내보내기에 적용할 우선순위입니다.
---

관리자 건물마스터의 입점부동산 값은 주소 매칭된 브로커 표준데이터를 우선한다. 표준데이터 매칭이 전혀 없을 때만 기존 상권정보 캐시를 참고용 폴백으로 사용한다. 도로명 매칭 결과가 있으면 지번 매칭 결과를 합치지 않는다.

**Why:** 같은 열에서 화면·합계·엑셀이 서로 다른 출처의 수를 보이면 관리자가 데이터 신뢰성을 판단하기 어렵고, 도로명·지번 양쪽에 걸리는 동일 업소를 중복 집계할 위험이 있다.

**How to apply:** 입점부동산의 이름·건수·합계·내보내기 등 동일한 사용자 개념을 새로 추가하거나 변경할 때, 브로커 우선 및 도로명 우선 규칙을 함께 적용한다. Python 정규화가 필요한 계산값은 서버 정렬을 제공하지 않는다.

공공데이터포털 브로커 API의 현재 응답은 최상위 `header`·`body` 구조이며 별도 영업상태 필드를 주지 않는다. 이 목록은 개업 사무소 목록이므로, 새로 수집한 행은 `영업중`으로 저장한다. 상태 필드가 제공되는 응답 변형은 그 원본값을 우선한다.

**Why:** 이전 `response` 래퍼 전제는 실제 수집을 중단시켰고, 기존 레코드의 주소 정규화 키와 상태가 갱신되지 않았다. 이미 저장된 과거 레코드의 상태는 외부 원본을 재수집하기 전에는 추정하면 안 된다.

**How to apply:** API 응답 형태를 변경할 때 실제 최상위/래퍼 구조와 상태 기본값을 함께 회귀 테스트한다. 재수집은 저장된 도로명·지번 정규화 키도 다시 채워 주소 표기 편차 매칭을 복구한다.

V-World 부동산중개업 파일은 D171이 업소·영업상태, D172가 소속 인력 원본이다. D170은 위치·주소·영업상태 Shapefile이며 전화번호 필드가 없다. D171의 전화번호도 현재 전체 공란이고, 개별 상세 화면에만 여러 번호가 보일 수 있다. 원본 등록번호는 전국에서 충돌하므로 지역·상호·주소를 포함한 내부키와 분리해 저장한다.

**Why:** 등록번호만 유일키로 쓰면 다른 지역 또는 충돌 업소가 덮어써지고, 상세 화면의 전화번호를 파일에서 얻을 수 있다고 가정하면 잘못된 전화번호 수집 경로를 만들게 된다.

**How to apply:** D171/D172 갱신은 지역코드·등록번호·상호로 연결하고 전화번호 배열은 상세 조회처럼 실제 번호를 제공하는 별도 원본에서만 채운다. 대량 ZIP 적재는 완전 중복키를 배치 안에서 제거하고 단계별 커밋한다.

기존 공공 API 행과 D171 행이 등록번호와 상호 또는 주소로 같은 업소임이 확인되면 기존 행을 기준으로 병합한다. 공공 API 전화번호는 보존하고 D171의 영업상태·정확한 등록일·주소 정규화 값을 보강한다. 번호만 같고 업소가 다른 충돌 행은 V-World 내부키로 계속 분리한다.

**Why:** D171 전화번호는 공란이므로 단순 UPSERT하면 이미 확보한 전화번호가 사라지고, 반대로 등록번호만으로 전부 합치면 실제 충돌 업소가 삭제된다.

**How to apply:** 병합 시 전화번호 필드는 UPDATE하지 않는다. 중복 정리는 실제 병합된 D171 결정적 내부키만 대상으로 하고, 인력은 상호 우선 연결 후 지역·등록번호가 양쪽에서 유일할 때만 보조 연결한다.
